# P1-05 · 泛型

> 目标:分清"必须会写的泛型"和"能读懂就行的类型体操",不被 Pi 里的硬核类型吓退
> 前置:[P1-03](P1-03-结构化类型.md)、[P1-04](P1-04-可辨识联合.md)
> 读完你应该能:看懂 `Model<TApi>` 里那个五层嵌套的条件类型,并解释 `defineTool` 的参数类型是怎么推导出来的

---

## 0. 先给你一颗定心丸

TS 泛型的**语法**和 Java 几乎一样,你已经会 80%:

```java
// Java
public <T extends Comparable<T>> T max(List<T> items) { ... }
```
```ts
// TS —— 几乎一模一样
function max<T extends Comparable<T>>(items: T[]): T { ... }
```

但 TS 的泛型**能力**比 Java 强一个数量级——它是一门**图灵完备的类型级编程语言**。你可以在类型层面做条件判断、遍历、递归。

**这一篇的策略**:
- **§1–§5 必须会写**——日常业务代码的量级,和 Java 差不多
- **§6–§9 能读懂就行**——Pi 里会用到,你不需要自己写
- **§10 知道有这回事**——极少数场景

不要试图一次全掌握。**读得懂比写得出重要。**

## 1. 基础:和 Java 一样的部分

```ts
// 泛型函数
function first<T>(items: T[]): T | undefined {
   return items[0];
}
first([1, 2, 3]);          // T 推导为 number,不用写 first<number>

// 泛型接口
interface Repository<T> {
   findById(id: string): Promise<T | undefined>;
   save(entity: T): Promise<void>;
}

// 泛型类
class Cache<K, V> {
   private map = new Map<K, V>();
   get(key: K): V | undefined { return this.map.get(key); }
   set(key: K, value: V): void { this.map.set(key, value); }
}
```

**约束 `extends`** —— 和 Java 的 `<T extends Xxx>` 一样:

```ts
interface Entity { id: string; }

function findIn<T extends Entity>(items: T[], id: string): T | undefined {
   return items.find(x => x.id === id);      // ✅ 因为约束了,能访问 .id
}
```

⚠️ **TS 没有 Java 的通配符 `?`**(`List<? extends Number>`)。TS 靠结构化类型和协变规则自动处理,大部分时候不用你操心。

---

## 2. 差异一:泛型参数可以有默认值

Java 没有这个:

```ts
class EventStream<T, R = T> { }         // R 不传就等于 T

interface Repository<T, ID = string> {   // ID 默认是 string
   findById(id: ID): Promise<T>;
}

const repo: Repository<Order> = ...;     // ID 自动是 string
```

Pi 里到处都是:

```ts
// packages/ai/src/utils/event-stream.ts:4
export class EventStream<T, R = T> implements AsyncIterable<T> { }

// packages/ai/src/types.ts:502
export interface Tool<TParameters extends TSchema = TSchema> { }
//                              ^^^^^^^^^^^^^^^^^ 约束      ^^^^^^^ 默认值

// packages/agent/src/types.ts:386
export interface AgentTool<TParameters extends TSchema = TSchema, TDetails = any> extends Tool<TParameters> { }
```

**为什么要默认值?** 让"不关心具体类型"的地方能简写:

```ts
const tools: AgentTool[] = [];              // 等价于 AgentTool<TSchema, any>[]
const t: AgentTool<typeof mySchema> = ...;  // 关心时才写
```

`AgentContext.tools` 就是这么声明的——收集一堆异构工具时不可能有统一的参数类型,用默认值兜住。

## 3. 差异二:类型推导强很多

```ts
// Java 需要显式或有限推导
Map<String, List<Order>> m = new HashMap<>();

// TS 从值反推,而且能推得很深
const m = new Map<string, Order[]>();

const grouped = orders.reduce((acc, o) => {
   (acc[o.status] ??= []).push(o);
   return acc;
}, {} as Record<string, Order[]>);        // 推导出 Record<string, Order[]>
```

**最重要的推导场景:从参数值反推泛型参数。** 这就是 P1-03 讲的 `defineTool` 能工作的原因:

```ts
const tool = defineTool({
   parameters: Type.Object({ sku: Type.String(), qty: Type.Number() }),
   //          ^^^^^^^^^^^^ TS 从这个【值】推出 TParams 的确切类型
   execute: async (id, params) => {
      params.sku;   // ✅ string
      params.qty;   // ✅ number
   },
});
```

推导链条:

```
你写的 Type.Object({...}) 这个值
  → TS 推出它的类型 TParams(一个具体的 TypeBox schema 类型)
  → execute 的 params 参数声明为 Static<TParams>
  → Static<> 把 schema 类型"翻译"成 { sku: string; qty: number }
  → IDE 有补全,写错报错
```

**Java 完全做不到这个。** 你没法从一个方法参数的值推导出另一个参数的类型。

### `Static<>`:schema 变类型

```ts
import { Type, type Static } from "typebox";

const OrderSchema = Type.Object({
   id: Type.String(),
   amountCents: Type.Number(),
   tags: Type.Array(Type.String()),
   remark: Type.Optional(Type.String()),
});

type Order = Static<typeof OrderSchema>;
// 等价于手写:
// { id: string; amountCents: number; tags: string[]; remark?: string }
```

**注意 `typeof OrderSchema`**——`OrderSchema` 是个**值**,`typeof` 拿到它的**类型**。这是值世界和类型世界之间的桥。

**一份定义,两个用途**:

```ts
// 运行时校验(相当于 Bean Validation)
Value.Check(OrderSchema, incomingJson);

// 编译期类型(相当于 DTO class)
function process(order: Order) { }
```

Java 里你要写一个 class + 一堆 `@NotNull` `@Min` 注解,类型和校验规则绑在一起但要靠注解处理器和反射。TS 里 schema 是普通的值,类型是从它算出来的——**单一真相源**。

这就是 Pi 定义工具参数的方式:

```ts
// packages/agent/src/harness/tools/read.ts:16
const readSchema = Type.Object({
   path: Type.String({ description: "Path to the file to read (relative or absolute)" }),
   offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
   limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});
```

那些 `description` 不是给人看的注释——**它们会被序列化成 JSON Schema 发给大模型**,模型靠它理解参数含义。所以这一个 schema 同时是:类型定义 + 运行时校验规则 + 给 LLM 的接口文档。**这个"一鱼三吃"是 Pi 设计里很聪明的一点。**

## 4. `keyof` / `typeof` / 索引访问

这三个是读懂后面所有内容的基础。

```ts
interface Order {
   id: string;
   amountCents: number;
   status: "pending" | "paid";
}

// ① keyof —— 拿到所有 key 组成的联合类型
type OrderKey = keyof Order;            // "id" | "amountCents" | "status"

// ② 索引访问 —— 拿某个字段的类型
type Status = Order["status"];          // "pending" | "paid"
type Any = Order[keyof Order];          // string | number | "pending" | "paid"

// ③ typeof(类型位置)—— 从值拿类型
const defaultOrder = { id: "O1", amountCents: 0 };
type DefaultOrder = typeof defaultOrder;   // { id: string; amountCents: number }
```

⚠️ **`typeof` 有两个含义,别混淆**:

```ts
if (typeof x === "string") { }      // ← 值位置:运行时判断类型,返回字符串
type T = typeof someValue;          // ← 类型位置:编译期取类型
```

**组合起来的经典用法**:类型安全的取值函数

```ts
function pluck<T, K extends keyof T>(obj: T, key: K): T[K] {
   return obj[key];
}

const s = pluck(order, "status");      // 类型精确是 "pending" | "paid"
const x = pluck(order, "nope");        // ❌ 报错:"nope" 不是 Order 的 key
```

Java 里这个函数只能返回 `Object`,而且 key 拼错了运行时才知道。

**Pi 里的用法**,`AgentMessage` 的定义([packages/agent/src/types.ts:325](../packages/agent/src/types.ts#L325)):

```ts
export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];
```

拆开看:
- `keyof CustomAgentMessages` → `"bashExecution" | "custom" | "branchSummary" | "compactionSummary"`
- `CustomAgentMessages[那个联合]` → 把这些 key 对应的**值类型**全取出来,组成联合

所以最终 `AgentMessage` = LLM 的三种消息 + 应用自定义的四种消息。**而且应用通过声明合并往 `CustomAgentMessages` 里加东西时,这个联合自动变宽**(见 P1-03 §7)。

## 5. 常用工具类型(必须会用)

这些是 TS 内置的,相当于类型层面的标准库:

```ts
interface Order {
   id: string;
   amountCents: number;
   remark?: string;
}

Partial<Order>              // 所有字段变可选 → 更新接口的入参
Required<Order>             // 所有字段变必填
Readonly<Order>             // 所有字段变只读
Pick<Order, "id" | "amountCents">    // 只挑这几个字段
Omit<Order, "remark">                // 排除这几个字段
Record<string, Order>                // { [k: string]: Order }

// 联合类型上的操作(P1-04 讲过)
Extract<"a" | "b" | "c", "a" | "b">  // "a" | "b"
Exclude<"a" | "b" | "c", "a">        // "b" | "c"
NonNullable<string | null>           // string

// 函数相关
ReturnType<typeof calcTotal>         // 函数返回值类型
Parameters<typeof calcTotal>         // 参数元组类型
Awaited<Promise<Order>>              // Order —— 剥掉 Promise
```

电商场景的典型用法:

```ts
// 创建订单:不需要传 id 和 createdAt(服务端生成)
type CreateOrderInput = Omit<Order, "id" | "createdAt">;

// 更新订单:所有字段可选,但 id 必填
type UpdateOrderInput = Partial<Omit<Order, "id">> & Pick<Order, "id">;
```

**Pi 里的真实用法**:

```ts
// packages/ai/src/types.ts:825 —— ImagesModel 复用 Model 但换掉几个字段
export interface ImagesModel<TApi extends ImagesApi>
   extends Omit<Model<Api>, "api" | "provider" | "reasoning" | "contextWindow" | "maxTokens" | "compat"> {
   api: TApi;
   provider: ImagesProviderId;
   output: ("text" | "image")[];
}
```

**读法**:"生图模型 = 聊天模型减掉这六个字段,再加上这三个"。一行搞定,而且 `Model` 加字段时 `ImagesModel` 自动跟着变。

Java 里你只能重新抄一遍所有字段,或者硬套继承(但继承没法"减字段")。

```ts
// packages/ai/src/models.ts:393 —— Required + Pick 组合
(provider): provider is Provider & Required<Pick<Provider, "refreshModels">> =>
```

**读法**:"Provider,并且它的 `refreshModels` 字段一定存在(不是可选)"。筛完之后调用就不用判空了。

## 6. 条件类型:`T extends X ? A : B`(能读懂就行)

**这是 Java 完全没有的东西**——在类型层面写 if/else。

```ts
type IsString<T> = T extends string ? "是" : "否";

type A = IsString<"hello">;    // "是"
type B = IsString<number>;     // "否"
```

电商例子:根据支付方式决定回调参数类型

```ts
type CallbackPayload<M> =
   M extends "alipay" ? { tradeNo: string; buyerId: string } :
   M extends "wechat" ? { transactionId: string; openId: string } :
   never;

function handleCallback<M extends "alipay" | "wechat">(method: M, payload: CallbackPayload<M>) { }

handleCallback("alipay", { tradeNo: "T1", buyerId: "B1" });   // ✅
handleCallback("alipay", { transactionId: "X" });             // ❌ 类型不匹配
```

### Pi 实战一:`ApiStreamOptions`

[packages/ai/src/types.ts:256](../packages/ai/src/types.ts#L256):

```ts
export interface ApiOptionsMap {
   "anthropic-messages": AnthropicOptions;
   "openai-completions": OpenAICompletionsOptions;
   "openai-responses": OpenAIResponsesOptions;
   "google-generative-ai": GoogleOptions;
   // ... 共 10 个
}

export type ApiStreamOptions<TApi extends Api> = TApi extends keyof ApiOptionsMap
   ? ApiOptionsMap[TApi]                        // 已知 API → 用它专属的选项类型
   : StreamOptions & Record<string, unknown>;   // 自定义 API 字符串 → 通用形状
```

**效果**:

```ts
ApiStreamOptions<"anthropic-messages">   // = AnthropicOptions,有 thinking 相关的字段
ApiStreamOptions<"my-custom-api">        // = 通用形状,允许任意字段
```

**解决的问题**:Pi 支持 10 种已知协议 + 任意自定义协议。已知的要有精确类型和自动补全,自定义的要能塞任意字段。条件类型让这两件事共存。

Java 里做不到——你只能用 `Map<String, Object>` 然后到处强转。

### Pi 实战二:嵌套五层的条件类型

[packages/ai/src/types.ts:814](../packages/ai/src/types.ts#L814),`Model` 的 `compat` 字段:

```ts
export interface Model<TApi extends Api> {
   id: string;
   api: TApi;
   // ...
   /** Compatibility overrides for OpenAI-compatible APIs. If not set, auto-detected from baseUrl. */
   compat?: TApi extends "openai-completions"
      ? OpenAICompletionsCompat
      : TApi extends "openai-responses" | "azure-openai-responses" | "openai-codex-responses"
         ? OpenAIResponsesCompat
         : TApi extends "anthropic-messages"
            ? AnthropicMessagesCompat
            : TApi extends "bedrock-converse-stream"
               ? BedrockCompat
               : never;
}
```

看着吓人,其实就是一串 if-else if-else:

```
if   TApi 是 openai-completions          → compat 的类型是 OpenAICompletionsCompat
elif TApi 是 三种 responses 之一          → OpenAIResponsesCompat
elif TApi 是 anthropic-messages          → AnthropicMessagesCompat
elif TApi 是 bedrock-converse-stream     → BedrockCompat
else                                     → never(即"这个 API 不支持 compat 字段")
```

**最后那个 `never` 很关键**:它表示"其他 API 根本不能有 compat 字段"(回忆 P1-04 §6 的 `?: never` 技巧)。

**实际效果**:

```ts
const m: Model<"google-generative-ai"> = {
   api: "google-generative-ai",
   compat: { ... },      // ❌ 报错!Google 的 API 没有兼容层
   // ...
};
```

**为什么值得这么复杂?** 因为 Pi 接了 40+ 个 provider,每家都有自己的怪癖(某家不支持 `anyOf`、某家的 thinking 格式不同…)。`compat` 就是"怪癖开关集合",但**不同协议的怪癖完全不同**。用条件类型能在编译期就保证你不会给 Google 的模型配 OpenAI 的兼容开关。

## 7. 映射类型:遍历所有 key(能读懂就行)

```ts
type Nullable<T> = { [K in keyof T]: T[K] | null };

type NullableOrder = Nullable<Order>;
// { id: string | null; amountCents: number | null; remark?: string | null }
```

`[K in keyof T]` 就是"对 T 的每个 key K",相当于类型层面的 for 循环。

`Partial`、`Required`、`Readonly`、`Pick` 全都是用映射类型实现的:

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
```

电商例子——把所有字段变成"查询条件":

```ts
type Query<T> = { [K in keyof T]?: T[K] | T[K][] };   // 支持单值或多值

type OrderQuery = Query<Order>;
const q: OrderQuery = { status: ["pending", "paid"], amountCents: 5997 };
```

## 8. Pi 里最硬核的一段(纯读懂,不用会写)

[packages/ai/src/model-catalog.ts](../packages/ai/src/model-catalog.ts) 整个文件只有 27 行,但把前面所有概念都用上了:

```ts
export type ModelGroups = Record<string, Record<string, object>>;

type ModelId<TGroups extends ModelGroups> = {
   [TApi in keyof TGroups]: keyof TGroups[TApi];
}[keyof TGroups] & string;

type ModelApi<TGroups extends ModelGroups, TModelId extends ModelId<TGroups>> = {
   [TApi in keyof TGroups]: TModelId extends keyof TGroups[TApi] ? TApi : never;
}[keyof TGroups] & Api;

export type ModelCatalog<TGroups extends ModelGroups, TProvider extends ProviderId> = {
   [TModelId in ModelId<TGroups>]: Model<ModelApi<TGroups, TModelId>> & {
      id: TModelId;
      provider: TProvider;
   };
};

export function flattenModelCatalog<const TProvider extends ProviderId, const TGroups extends ModelGroups>(
   _provider: TProvider,
   groups: TGroups,
): ModelCatalog<TGroups, TProvider> {
   return Object.assign({}, ...Object.values(groups)) as ModelCatalog<TGroups, TProvider>;
}
```

**先看它要解决什么问题。** 输入的数据长这样(按 API 分组):

```ts
{
   "anthropic-messages": {
      "claude-opus-4-5":   { /* 模型元数据 */ },
      "claude-sonnet-4-6": { /* ... */ },
   },
   "openai-completions": {
      "gpt-4o-mini": { /* ... */ },
   },
}
```

期望的输出是**扁平**的,而且每个模型的 `api` 字段类型要精确:

```ts
{
   "claude-opus-4-5":   Model<"anthropic-messages">,     // ← api 类型精确
   "claude-sonnet-4-6": Model<"anthropic-messages">,
   "gpt-4o-mini":       Model<"openai-completions">,
}
```

**逐个拆解**:

```ts
type ModelId<TGroups> = { [TApi in keyof TGroups]: keyof TGroups[TApi] }[keyof TGroups] & string;
```

1. `{ [TApi in keyof TGroups]: keyof TGroups[TApi] }` —— 映射类型,得到
   `{ "anthropic-messages": "claude-opus-4-5" | "claude-sonnet-4-6", "openai-completions": "gpt-4o-mini" }`
2. `[keyof TGroups]` —— **索引访问一个联合**,把所有值取出来合并:
   `"claude-opus-4-5" | "claude-sonnet-4-6" | "gpt-4o-mini"`
3. `& string` —— 保证结果是字符串(object 的 key 也可能是 symbol)

**这就是"把嵌套的 key 拍平成一个联合"的标准套路**,`{...}[keyof ...]` 这个组合你会反复见到。

```ts
type ModelApi<TGroups, TModelId> = { [TApi in keyof TGroups]: TModelId extends keyof TGroups[TApi] ? TApi : never }[keyof TGroups] & Api;
```

反向查找:**给一个模型 id,找出它属于哪个 API**。

对每个 API 判断"这个模型 id 在不在你下面",在就返回 API 名,不在返回 `never`。然后同样用 `[keyof TGroups]` 合并——因为 `never` 在联合里会自动消失,最后只剩下匹配的那一个。

**`never` 在联合中被吸收**(`"a" | never` = `"a"`)是个很有用的性质,这里就是靠它做过滤。

最后 `flattenModelCatalog` 的**运行时实现只有一行**:

```ts
return Object.assign({}, ...Object.values(groups)) as ModelCatalog<TGroups, TProvider>;
```

就是把几个对象合并。**所有的复杂度都在类型层面,运行时零开销。**

**回报是什么?**

```ts
const model = getBuiltinModel("anthropic", "claude-opus-4-5");
// model 的类型精确是 Model<"anthropic-messages">
// → 于是 model.compat 的类型精确是 AnthropicMessagesCompat
// → 于是 IDE 里 model.compat. 的补全只显示 Anthropic 相关的开关
```

**从一个字符串字面量,一路推导到深层字段的精确类型。** Java 做不到,这是 TS 类型系统真正独特的价值。

> 你现在**不需要会写**这种代码。但知道"这一块是纯类型层面的推导,运行时只有一行 `Object.assign`"就够了——读源码时可以直接跳过。

## 9. `const` 泛型参数(TS 5.0+)

注意上面 `flattenModelCatalog` 的签名里有个 `const`:

```ts
export function flattenModelCatalog<const TProvider extends ProviderId, const TGroups extends ModelGroups>(
```

作用:让 TS 用**字面量类型**推导,而不是放宽:

```ts
// 没有 const
function f<T>(x: T): T { return x; }
const a = f(["a", "b"]);          // a: string[]

// 有 const
function g<const T>(x: T): T { return x; }
const b = g(["a", "b"]);          // b: readonly ["a", "b"]  ← 精确!
```

相当于自动加了 `as const`(P1-00 §12)。没有它,`flattenModelCatalog` 拿到的就是 `Record<string, ...>`,所有模型 id 的精确类型全丢了。

## 10. 协变与逆变(知道有这回事)

```ts
class Animal {}
class Dog extends Animal {}

let animals: Animal[] = [];
let dogs: Dog[] = [];

animals = dogs;      // ✅ TS 允许(数组协变)
```

⚠️ **这在理论上不安全**(你可以往 `animals` 里塞一只 Cat,而它实际是 `dogs`)。TS 为了实用性**故意放行**,Java 也一样(数组协变是 Java 的历史遗留问题,`ArrayStore` 异常就是这么来的)。

**函数参数的规则**才是真正容易困惑的:

```ts
type Handler = (order: Order) => void;

const h1: Handler = (o: Order) => { };            // ✅
const h2: Handler = (o: { id: string }) => { };   // ✅ 参数更宽松,安全
const h3: Handler = (o: PaidOrder) => { };        // ⚠️ 参数更严格,理论上不安全但 TS 默认允许
```

`strictFunctionTypes` 选项能收紧 h3 这种情况(但只对函数类型生效,对方法签名不生效)。

**实用建议:知道有这回事就行,遇到"为什么这个能赋值/不能赋值"的困惑时回来查。** 日常业务代码基本不会撞上。

## 12. 常见坑速查

| 坑 | 症状 | 解法 |
|---|---|---|
| 泛型参数没约束就访问字段 | "T 上不存在属性 id" | 加 `T extends { id: string }` |
| 手写类型标注导致推导失效 | 参数变成 `any` 或通用类型 | 用恒等函数(`defineTool`)模式 |
| 混淆两种 `typeof` | 语法报错 | 值位置=运行时判断,类型位置=取类型 |
| 忘了 `typeof` 直接用值当类型 | "xxx 指的是值,但在此处用作类型" | 写 `typeof xxx` |
| 条件类型里 `never` 被吸收没预期到 | 联合类型少了一项 | 这是特性,用来做过滤 |
| 想写复杂类型体操但写不出 | 卡住半天 | **先用 `any` 跑通业务,回头再收紧**;类型体操不是必须的 |
| 泛型用在不需要的地方 | 代码难读没收益 | 只有一处用到的泛型参数通常是多余的 |

**最后一条特别重要**:泛型的目的是**在多个位置之间建立类型关联**。如果一个泛型参数只出现一次,它就没有意义:

```ts
function bad<T>(x: T): void { }        // ❌ T 只出现一次 = 等于 unknown
function good<T>(x: T): T[] { }        // ✅ T 关联了参数和返回值
```
