# P1-03 · 结构化类型(Structural Typing)

> 目标:理解"形状匹配即兼容",以及它如何让 Pi 不需要 DI 容器
> 前置:[P1-00](P1-00-JS-TS语法热身.md)
> 读完你应该能:解释 Pi 的 `defineTool` 为什么是个"什么都不做"的函数,以及 `ReadOperations` 这种端口注入为什么不需要框架

---

## 0. 一句话总结

**Java 看"你声明实现了什么"(名义类型),TS 看"你长什么样"(结构类型)。**

```java
// Java:必须显式声明
class OrderService implements OrderApi { }     // 不写 implements 就不算
```

```ts
// TS:长得像就行
interface OrderApi { findById(id: string): Order; }

const service = {                              // 没有任何 implements
   findById: (id: string) => ({ id, amountCents: 0 }),
};

const api: OrderApi = service;                 // ✅ 合法!形状匹配
```

这是 TS 类型系统的地基,理解它才能看懂 Pi 为什么写成那个样子。

---

## 1. 名义 vs 结构:一个电商例子

假设我们有两个来源的"订单"类型,字段完全一样:

```ts
// 内部领域模型
interface Order {
   id: string;
   amountCents: number;
}

// 外部 API 的 DTO
interface OrderDTO {
   id: string;
   amountCents: number;
}
```

在 Java 里,这是两个**完全不兼容**的类,必须写转换代码(或者上 MapStruct)。

在 TS 里:

```ts
const dto: OrderDTO = { id: "O1", amountCents: 5997 };
const order: Order = dto;        // ✅ 直接赋值,零转换
```

**因为 TS 只看形状。** `OrderDTO` 有 `Order` 要求的全部字段,类型就兼容。名字叫什么完全无关。

这带来两个后果:

- **好处**:大量的样板转换代码消失了
- **坏处**:语义不同但形状相同的类型会**意外兼容**(§6 会讲怎么防)

## 2. 兼容规则:目标要什么,来源有就行

```ts
interface Shipment {
   orderId: string;
   address: string;
}

// ① 字段多了 —— 兼容
const rich = { orderId: "O1", address: "北京", weight: 2.5, remark: "易碎" };
const s1: Shipment = rich;        // ✅ 多余字段无所谓

// ② 字段少了 —— 不兼容
const poor = { orderId: "O1" };
const s2: Shipment = poor;        // ❌ 缺 address

// ③ 类型不对 —— 不兼容
const wrong = { orderId: 123, address: "北京" };
const s3: Shipment = wrong;       // ❌ orderId 应该是 string
```

**记忆口诀:目标类型是"最低要求",来源满足就行,多的不管。**

这正好对应 Java 的里氏替换:子类可以有更多方法。只是 TS 不要求你声明继承关系。

### ⚠️ 例外:对象字面量的"额外属性检查"

规则 ① 有个坑,只在**直接写字面量**时触发:

```ts
const s4: Shipment = {
   orderId: "O1",
   address: "北京",
   weight: 2.5,          // ❌ 报错!"weight 不在 Shipment 类型中"
};
```

同样是多字段,为什么这次报错?

因为 TS 认为:**你直接手写字面量还多写了字段,大概率是拼错了或者用错了类型**,所以额外收紧检查,帮你抓 bug。而通过变量赋值(规则 ①)说明这个对象有独立来源,就放行。

**三种绕过方式**:

```ts
// 1. 先赋给变量(最自然)
const tmp = { orderId: "O1", address: "北京", weight: 2.5 };
const a: Shipment = tmp;                         // ✅

// 2. 用 satisfies(推荐,见 P1-00 §12)
const b = { orderId: "O1", address: "北京" } satisfies Shipment;

// 3. 在类型里允许扩展
interface Shipment { orderId: string; address: string; [key: string]: unknown; }
```

Pi 里就用了第 3 种思路:

```ts
// packages/ai/src/types.ts:221
export type ProviderStreamOptions = StreamOptions & Record<string, unknown>;
```

`& Record<string, unknown>` 的意思是"除了 `StreamOptions` 的字段,还可以带任意其他字段"。因为不同 provider 有各自的私有选项,不可能穷举。

## 3. 最大的好处:对象字面量就是"实现类"

Java 里要实现一个接口,你得建个类:

```java
public class ReadTool implements Tool {
    @Override public String getName() { return "read"; }
    @Override public Result execute(Params p) { ... }
}
```

TS 里直接写个对象就行:

```ts
interface Tool {
   name: string;
   description: string;
   execute: (params: unknown) => Promise<string>;
}

const readTool: Tool = {
   name: "read",
   description: "读取文件",
   execute: async (params) => "文件内容",
};
```

**没有 class,没有 implements,没有 @Override。** 这就是为什么 Pi 里的工具全是对象字面量。

看 Pi 最小的扩展示例,[packages/coding-agent/examples/extensions/hello.ts](../packages/coding-agent/examples/extensions/hello.ts) 全文:

```ts
import { Type } from "@earendil-works/pi-ai";
import { defineTool, type ExtensionAPI } from "@earendil-works/pi-coding-agent";

const helloTool = defineTool({
   name: "hello",
   label: "Hello",
   description: "A simple greeting tool",
   parameters: Type.Object({
      name: Type.String({ description: "Name to greet" }),
   }),

   async execute(_toolCallId, params, _signal, _onUpdate, _ctx) {
      return {
         content: [{ type: "text", text: `Hello, ${params.name}!` }],
         details: { greeted: params.name },
      };
   },
});

export default function (pi: ExtensionAPI) {
   pi.registerTool(helloTool);
}
```

**一个工具就是一个对象。** 26 行,零继承,零注解。

## 4. 揭秘:`defineTool` 为什么是个"什么都不做"的函数?

看它的实现([packages/coding-agent/src/core/extensions/types.ts:509](../packages/coding-agent/src/core/extensions/types.ts#L509)):

```ts
export function defineTool<TParams extends TSchema, TDetails = unknown, TState = any>(
   tool: ToolDefinition<TParams, TDetails, TState>,
): ToolDefinition<TParams, TDetails, TState> & AnyToolDefinition {
   return tool as ToolDefinition<TParams, TDetails, TState> & AnyToolDefinition;
}
```

**它把参数原样返回。运行时零作用。** 那要它干嘛?

答案:**为了让 TS 能同时做"类型检查"和"类型推导"。**

对比三种写法:

```ts
// 写法 A:啥都不标注
const tool1 = {
   name: "hello",
   parameters: Type.Object({ name: Type.String() }),
   execute: async (id, params) => { params.name },   // ❌ TS7006: 参数 params 隐式具有 any 类型
};
// Pi 开了 strict,这里直接编译不过。若关掉 noImplicitAny,则 params 静默变 any——
// 更糟,因为拼错字段名也不报错

// 写法 B:显式标注类型
const tool2: ToolDefinition<TSchema> = {
   name: "hello",
   parameters: Type.Object({ name: Type.String() }),
   execute: async (id, params) => { params.name },   // ❌ TS18046: params 的类型是 unknown
};
// 问题:一旦把 TParams 钉死成通用的 TSchema,Static<TSchema> 就退化成 unknown,
// 推导链断掉。注意是 unknown 不是 any——编译器会拦住你,但你也拿不到字段

// 写法 C:defineTool(两全其美)
const tool3 = defineTool({
   name: "hello",
   parameters: Type.Object({ name: Type.String() }),
   execute: async (id, params) => { params.name },   // ✅ params.name 是 string,有补全!
});
```

**关键在于:泛型参数 `TParams` 是从你传入的 `parameters` 字段推导出来的**,然后 `execute` 的 `params` 参数类型又是从 `TParams` 算出来的。

```
你写 Type.Object({ name: Type.String() })
   → TS 推导出 TParams = 那个具体 schema 的类型
   → execute 的 params 类型 = Static<TParams> = { name: string }
   → IDE 里 params.name 有补全,拼错会报错
```

如果你手动写类型标注,就把 `TParams` 钉死成通用的 `TSchema` 了,推导链断掉。

**这个"恒等函数用于类型推导"是 TS 的经典模式**,你会在很多库里见到(`defineConfig`、`defineComponent`、`createSlice`…)。看到 `defineXxx({...})` 就知道:它运行时什么都不做,存在的意义纯粹是类型。

Java 里没有对应物,因为 Java 没有这种"从参数值反推泛型参数再约束另一个参数"的能力。

## 5. 端口注入:不需要 DI 容器

这是结构化类型在 Pi 里最有价值的应用。

### 电商版:先看你熟悉的 Spring 写法

```java
@Service
public class OrderService {
    @Autowired private OrderRepository repo;      // 容器帮你注入
    // 测试时要 @MockBean 或者 Mockito
}
```

### Pi 的写法

看 [packages/coding-agent/src/core/tools/read.ts:49](../packages/coding-agent/src/core/tools/read.ts#L49):

```ts
export interface ReadOperations {
   /** Read file contents as a Buffer */
   readFile: (absolutePath: string) => Promise<Buffer>;
   /** Check if file is readable (throw if not) */
   access: (absolutePath: string) => Promise<void>;
   /** Detect image MIME type, return null or undefined for non-images */
   detectImageMimeType?: (absolutePath: string) => Promise<string | null | undefined>;
}

const defaultReadOperations: ReadOperations = {
   readFile: (path) => fsReadFile(path),
   access: (path) => fsAccess(path, constants.R_OK),
   detectImageMimeType: detectSupportedImageMimeTypeFromFile,
};

export interface ReadToolOptions {
   autoResizeImages?: boolean;
   operations?: ReadOperations;              // ← 注入点
}
```

用的时候:

```ts
// read.ts:214
const ops = options?.operations ?? defaultReadOperations;
```

**就这么简单。** 没有容器,没有注解,没有 `@Autowired`。默认用本地文件系统,想换就传一个。

**结构化类型让这件事变得几乎零成本**:任何有 `readFile` 和 `access` 这两个方法的对象都能塞进去,不需要 `implements ReadOperations`。

```ts
// 让 read 工具走 SSH 读远程文件
const sshTool = createReadTool(cwd, {
   operations: {
      readFile: (p) => sshClient.readFile(p),
      access: (p) => sshClient.stat(p).then(() => {}),
   },
});

// 测试时用内存文件系统,零依赖
const memFs = new Map<string, string>([["/a.ts", "hello"]]);
const testTool = createReadTool("/", {
   operations: {
      readFile: async (p) => Buffer.from(memFs.get(p) ?? ""),
      access: async (p) => { if (!memFs.has(p)) throw new Error("ENOENT"); },
   },
});
```

**这就是"端口与适配器"(Ports & Adapters / 六边形架构)**,你在 Java 里应该熟悉这个概念——只是 Java 需要接口 + 实现类 + 配置类三样东西,TS 里一个对象字面量就完事。

Pi 里这类端口有一堆,都是同一个模式:

| 端口 | 位置 | 抽象了什么 |
|---|---|---|
| `ReadOperations` | `coding-agent/src/core/tools/read.ts` | 文件读取 |
| `ExecutionEnv` | `agent/src/harness/types.ts` | 文件系统 + shell |
| `SessionStorage` | `agent/src/harness/session/types.ts` | 会话持久化 |
| `StreamFn` | `agent/src/types.ts:28` | **整个 LLM 调用**(只是一个函数!) |
| `CredentialStore` | `ai/src/auth/types.ts` | 凭据存储 |
| `Terminal` | `tui/src/terminal.ts` | 终端 I/O |

注意 `ExecutionEnv` 的定义精简到极致:

```ts
// packages/agent/src/harness/types.ts
export interface ExecutionEnv extends FileSystem, Shell {}
```

**接口可以多继承**(Java 也可以),这里就是把两个能力拼起来,不加任何新东西。

`StreamFn` 更极端——它连接口都不是,就是一个**函数类型**:

```ts
export type StreamFn = (
	model: Model<Api>,
	context: Context,
	options?: SimpleStreamOptions,
) => AssistantMessageEventStream | Promise<AssistantMessageEventStream>;
```

**最小的端口就是一个函数。** 结构化类型下,任何签名匹配的函数都能当实现,包括箭头函数、类方法、mock。这就是为什么 `packages/agent` 能完全不知道 HTTP 的存在。

## 6. ⚠️ 陷阱:意外兼容

结构化类型的代价是**语义不同但形状相同的类型会互相兼容**。

```ts
type UserId = string;
type OrderId = string;

function cancelOrder(id: OrderId) { }

const userId: UserId = "U888";
cancelOrder(userId);      // ✅ 编译通过!但这是个 bug
```

电商里这种"ID 传错"的事故非常常见。Java 里你可以包一层 `record OrderId(String value)`,TS 里怎么办?

**方案:品牌类型(branded type)**

```ts
type Brand<T, B extends string> = T & { readonly __brand: B };

type UserId  = Brand<string, "UserId">;
type OrderId = Brand<string, "OrderId">;

// 构造函数(唯一的入口)
const toOrderId = (s: string): OrderId => s as OrderId;
const toUserId  = (s: string): UserId  => s as UserId;

function cancelOrder(id: OrderId) { }

const uid = toUserId("U888");
cancelOrder(uid);              // ❌ 现在报错了!类型不兼容
cancelOrder(toOrderId("O1"));  // ✅
```

原理:`__brand` 字段**运行时根本不存在**(只是类型层面的标记),但它让两个类型在结构上不再相同。零运行时开销,纯编译期约束。

**什么时候值得用?** 同类型但绝不能混用的值:各种 ID、货币金额(分 vs 元)、已校验/未校验的输入。

Pi 里那个 `string & {}` 其实是同一族技巧的变体:

```ts
// packages/ai/src/types.ts:29
export type Api = KnownApi | (string & {});
```

只不过目的相反——不是为了区分,是为了**在允许任意字符串的同时保留自动补全**。

## 7. `interface` vs `type`:该用哪个

两者在结构化类型下**几乎等价**:

```ts
interface Order { id: string; }
type Order2 = { id: string; };

const a: Order = { id: "1" };
const b: Order2 = a;              // ✅ 互相兼容
```

区别:

| | `interface` | `type` |
|---|---|---|
| 描述对象形状 | ✅ | ✅ |
| 联合类型 `A \| B` | ❌ | ✅ |
| 交叉类型 `A & B` | 用 `extends` | ✅ |
| 映射/条件类型 | ❌ | ✅ |
| **声明合并**(同名自动合并) | ✅ | ❌ |
| 报错信息可读性 | 略好 | 略差 |

**Pi 的实际用法**(557 个 interface,346 个 type):

- **对象形状 → `interface`**:`Order`、`Tool`、`ReadOperations`、`AgentState`
- **联合、别名、函数类型、类型运算 → `type`**:`Message`、`AssistantMessageEvent`、`StreamFn`、`ApiStreamOptions`

**唯一一处必须用 `interface` 的场景是声明合并**,Pi 用它做了一个很漂亮的扩展点:

```ts
// packages/agent/src/types.ts:316
export interface CustomAgentMessages {
   // Empty by default - apps extend via declaration merging
}

export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];
```

默认是空的。然后 coding-agent 在自己的文件里"往里加东西":

```ts
// packages/coding-agent/src/core/messages.ts:70
declare module "@earendil-works/pi-agent-core" {
   interface CustomAgentMessages {
      bashExecution: BashExecutionMessage;
      custom: CustomMessage;
      branchSummary: BranchSummaryMessage;
      compactionSummary: CompactionSummaryMessage;
   }
}
```

**效果:上游的 `AgentMessage` 类型自动包含了下游新增的消息类型**,而上游代码一行都没改。

Java 里完全没有对应物——你没法从外部往一个 interface 里加方法。最接近的是编译期注解处理器,但那要重量级得多。

这个设计对应的是"开放封闭原则":`agent` 包对扩展开放(任何应用能加自己的消息类型),对修改封闭(agent 包自己不用动)。

## 8. class 也遵守结构化规则

```ts
class LocalRepo {
   async load(id: string): Promise<Order> { return { id, amountCents: 0 }; }
}

interface OrderRepo {
   load(id: string): Promise<Order>;
}

const repo: OrderRepo = new LocalRepo();     // ✅ 没写 implements,照样兼容
```

甚至两个无关的 class 之间也兼容:

```ts
class A { greet() { return "a"; } }
class B { greet() { return "b"; } }

const a: A = new B();      // ✅ 形状一样就行
```

**但 `private` 字段会打破这个规则**:

```ts
class A { private secret = 1; }
class B { private secret = 1; }

const a: A = new B();      // ❌ 报错!private 字段来源不同
```

TS 特意让 `private`/`protected` 成为"名义"的,给你一个制造不兼容的手段。这其实是另一种"品牌类型"。

**那还要不要写 `implements`?** 要,但目的不同:

```ts
class LocalRepo implements OrderRepo {       // ← 加了这个
   async load(id: string) { ... }
}
```

`implements` 在 TS 里**不影响类型兼容性**(不写也兼容),它的作用是**让编译器立刻检查你有没有实现全**,而不是等到赋值时才报错。**是一种主动的自检,不是必需的声明。**

Pi 里两种都有:

```ts
// packages/ai/src/utils/event-stream.ts:4
export class EventStream<T, R = T> implements AsyncIterable<T> {
```

这里写 `implements` 是为了确保 `[Symbol.asyncIterator]` 方法签名正确——写错了当场报错,而不是等到有人 `for await` 时才发现。

## 9. 常见坑速查

| 坑 | 症状 | 解法 |
|---|---|---|
| 直接写字面量多了字段 | "对象字面量只能指定已知属性" | 先赋给变量,或用 `satisfies` |
| 两个语义不同的 ID 混用 | 编译通过但运行时逻辑错 | 品牌类型 |
| 以为不写 `implements` 就不兼容 | 意外的赋值成功 | 理解结构化规则;需要隔离用 `private` 或品牌 |
| `type` 想用声明合并 | 报错"重复标识符" | 改用 `interface` |
| 用 `interface` 写联合类型 | 语法错误 | 联合必须用 `type` |
| 手动标注类型导致推导失效 | 参数变成 `any` 或通用类型 | 用 `defineXxx()` 恒等函数模式 |
