## 一、开篇：三个必须先建立的认知

在打开任何一个 `.ts` 文件之前，先把这三件事想清楚。想不清楚就往下读代码，会非常痛苦。

### 1.1 Agent 的本质是一个 while 循环

```
while (true) {
    响应 = 问大模型(上下文)                 // 1. 一次 HTTP 请求
    if (响应里没有工具调用) break            // 2. 模型说完了 → 结束
    结果 = 执行工具(响应里要求的工具调用)      // 3. 模型说"帮我调 read(path=...)"，你的代码去执行
    上下文.追加(响应, 结果)                  // 4. 结果塞回上下文，进入下一轮
}
```

就这些。Pi 的核心循环在 [packages/agent/src/agent-loop.ts](../packages/agent/src/agent-loop.ts) 的 `runLoop()`，第 155–275 行。整个文件 796 行，多出来的部分全是：错误处理、取消、事件广播、钩子、并发调度、消息插队。**骨架只有上面 4 行。**

**最容易犯的认知错误**：以为大模型会"执行"东西。它不会。模型只会在响应里吐出一段 JSON，语义是「我想调用名叫 `read`、参数是 `{"path":"a.ts"}` 的函数」。真正打开文件的是你的 TypeScript 代码。模型甚至不知道这个函数存不存在——它只是照着你在请求里附带的工具描述（JSON Schema）猜了一个调用。

Java 类比：你在一个 while 循环里反复调一个远程 RPC。这个 RPC 有时返回最终答案，有时返回「请你在本地执行 `orderService.query(id=123)`，然后把结果告诉我」。你执行完，把结果作为下一次请求的一部分发回去，直到它不再要求你干活。

### 1.2 十个包，但只有三个是主线

`packages/` 下有 **10 个目录**。README 只重点介绍三个，是因为那三个是**使用者会 `npm install` 的东西**，不代表其他七个不重要。

先把全貌摆出来（按依赖分层，`src` 行数不含测试）：

| 层 | 包 | src 行数 | 依赖谁 | 是什么 |
|---|---|---|---|---|
| **0** | `telemetry` | 935 | — | 埋点契约。只有接口和类型，没有实现，也不绑定任何后端 |
| **0** | `protocol` | 1,236 | — | 远程会话的线上协议：CBOR 编码 + 4 字节长度前缀分帧 |
| **0** | `tui` | 16,733 | — | 终端 UI 库，差分渲染。**和 AI 完全无关**，可以独立学 |
| **1** | `ai` | 23,156 | telemetry | ★ LLM 统一 API：20+ provider、10 种线上协议、流式、工具调用 |
| **1** | `client` | 1,225 | protocol | 远程会话客户端（传输层无关，浏览器也能跑） |
| **2** | `agent` | 12,635 | ai, telemetry | ★ Agent 运行时：循环、工具编排、状态、会话树 |
| **2** | `server` | 2,299 | ai, protocol | 远程会话服务端（实验中） |
| **3** | `session-backends/sqlite-node` | 2,389 | ai, agent | SQLite 会话存储后端。**单独成包是为了不让核心包依赖原生 SQLite** |
| **3** | `coding-agent` | 59,014 | agent, ai, client, protocol, tui | ★ 产品层：CLI 编码 agent |
| 旁挂 | `evals` | 1,277 | ai, coding-agent | 行为评测。唯一不发布到 npm 的包（`private: true`） |

**关于那个第 10 个目录**：`session-backends/` 本身不是一个包，它是个**容器目录**，里面装着 `sqlite-node` 一个包（根 `package.json` 的 workspaces 里单独写了 `"packages/session-backends/*"`）。所以是 10 个目录 = 10 个包，只是有一个嵌套了一层。这种「预留分组」的做法说明作者打算以后加 Postgres 等其他后端。

**为什么 README 只讲三个**：`coding-agent` 是产品，`agent` 和 `ai` 是可以被别人拿去用的库。其余七个要么是支撑库（`tui`、`telemetry`）、要么是还在实验的远程会话栈（`protocol` + `client` + `server`）、要么是基础设施（`sqlite-node`）、要么是内部工具（`evals`）。

**对你的学习意义**，这 10 个包分三档：

- **必读主线（P2–P4）**：`ai` → `agent` → `coding-agent`
- **按需切入（P5 自选）**：`tui`（纯工程，很优雅）、`protocol`/`client`/`server`（自定义二进制协议）、`sqlite-node`（存储后端 + 一致性测试套件）
- **可以最后看**：`telemetry`（几乎没有逻辑）、`evals`（等你要验证「改了提示词是不是变好了」时再看）

主线的依赖是**严格单向**的：`ai ← agent ← coding-agent`。这跟 Spring 项目里 `domain ← service ← controller` 是一个道理。所以学习顺序也自底向上：先搞懂 `ai` 在跟大模型说什么，再搞懂 `agent` 怎么把它变成循环，最后看 `coding-agent` 怎么把它变成一个能用的产品。

**顺便注意一个信号**：这个项目的测试量和源码量基本 1:1，`ai` 甚至是 34,354 行测试对 23,156 行源码。也就是说**测试是这个项目最完整的一份规格说明**。后面 P3 阶段我把 `agent/test/agent-loop.test.ts` 列为必读，就是这个原因。

其中 `agent` 和 `ai` 之间的接缝窄到只有**一个函数类型**——`StreamFn`（[packages/agent/src/types.ts:28](../packages/agent/src/types.ts#L28)）：

```ts
export type StreamFn = (model, context, options?) =>
    AssistantMessageEventStream | Promise<AssistantMessageEventStream>;
```

`agent` 包从头到尾没有构造过一个 HTTP 客户端，也没 import 过任何 provider。它只知道「给我一个能把 context 变成事件流的函数」。这是整个项目最漂亮的一处设计，值得反复琢磨。

### P1 — TypeScript 生存包（5–8 天）

**原则：不要先啃三周语法书。** 你已经是熟练工程师，需要的只是「Java 没有 / 不一样」的那部分。

**必须掌握的 8 个点**

1. **模块系统（ESM）**：`import` / `export`，没有 package 和 classpath，路径即身份。注意 Pi 用的是显式 `.ts` 后缀（`import ... from "./types.ts"`），这是 Node 原生 TS 剥离模式的要求。
2. **`async` / `await` / `Promise`**：等价于 `CompletableFuture`，但**只有一个线程**。`await` 不阻塞线程，它挂起当前函数，把控制权还给事件循环。没有 `synchronized`，因为不存在抢占——但也因此，任何 `await` 之后状态都可能已经变了。
3. **结构化类型（duck typing）**：TS 的 `interface` 不需要 `implements` 就能赋值，只要形状匹配。这是跟 Java 最根本的差异，也是 Pi 大量用「对象字面量当组件」的原因。
4. **可辨识联合（discriminated union）**：`type Event = {type:"a", ...} | {type:"b", ...}`，配 `switch (e.type)` 做穷尽匹配。这就是 Java 21 的 sealed interface + record + pattern matching，但 TS 里用得更随意、更频繁。Pi 里有 80 多处。
5. **泛型的差异**：写法像 Java，但可以做条件类型、映射类型、字面量类型运算。Pi 用它做了很硬核的事（比如 `getBuiltinModel("anthropic", "claude-opus-4-5")` 能精确推导出 `Model<"anthropic-messages">`）。**先能读懂，不用会写。**
6. **`AsyncIterable` + `for await`**：等价于响应式流，但没有背压框架。Pi 用它传流式事件。
7. **`AbortSignal` / `AbortController`**：等价于 `Thread.interrupt()` + 协作式取消，但是显式传递的。Pi 里出现 269 次——**这是这个代码库最重要的横切关注点**。
8. **`unknown` vs `any`**：`unknown` 是安全的 `Object`（必须先收窄才能用），`any` 是关掉类型检查的逃生舱。Pi 的规约允许 `any` 但尽量少用。

**工具链地图**（对应你熟悉的东西）

| Pi 用的 | Java 世界的对应物 |
|---|---|
| npm workspaces（`packages/*`） | Maven / Gradle 多模块 |
| `package.json` | `pom.xml` |
| `package-lock.json` | 锁定版本的依赖树；Pi 把它当作代码审查对象 |
| `tsc` / `tsgo`（`npm run check`） | `javac` + 静态检查 |
| Biome（`biome.json`） | Checkstyle + Spotless（lint + 格式化二合一） |
| Vitest | JUnit |
| `tsx` | 直接跑源码，类似 `mvn exec` 但零编译 |
| esbuild | 打包器，无 Java 对应物 |

**怎么练**：不要写 toy 项目。直接拿 [packages/ai/src/types.ts](../packages/ai/src/types.ts)（830 行，纯类型声明，无逻辑）逐行啃。看不懂的语法当场查。这一个文件覆盖了你 80% 会遇到的 TS 语法。

### P2 — LLM API 层：`packages/ai`（7–10 天）

这一层的职责：把 20 多家厂商、10 种不同的 HTTP 协议，收敛成一套统一的消息模型和事件流。

**三个概念必须分清**（这是理解整个包的钥匙）

| 概念 | 是什么 | 数量 | 位置 |
|---|---|---|---|
| **API** | 线上协议（wire format） | ~10 种 | `src/api/*.ts` |
| **Provider** | 运行单元 = 目录 + 认证 + baseUrl | 40+ 个 | `src/providers/*.ts` |
| **Models** | 注册表 / 容器，按 `model.api` 分发 | 1 个 | `src/models.ts` |

关键洞察：**很多 Provider 共用同一个 API**。xAI、Groq、Cerebras、OpenRouter、DeepSeek 全都用 `openai-completions` 这一套线上协议。所以 provider 文件普遍只有 15–60 行，而 api 文件动辄 1000+ 行。

Spring 类比：API 是接口，Provider 是配置好的 Bean 定义，Models 是 ApplicationContext。

**阅读顺序**

| # | 文件 | 行数 | 为什么读它 |
|---|---|---|---|
| 1 | [packages/ai/src/types.ts](../packages/ai/src/types.ts) | 830 | 整个领域模型都在这一个文件里。后面所有代码都是它的实现 |
| 2 | [packages/ai/src/utils/event-stream.ts](../packages/ai/src/utils/event-stream.ts) | 88 | 整个包怎么交付结果就靠它。推拉队列 + `AsyncIterable`，替代 Java 的响应式流 |
| 3 | [packages/ai/README.md](../packages/ai/README.md) §Quick Start | — | 消费侧的标准写法，读完类型马上看到用法 |
| 4 | [packages/ai/src/providers/anthropic.ts](../packages/ai/src/providers/anthropic.ts) | 59 | 最小的完整 provider，三层抽象怎么拼在一起 |
| 5 | [packages/ai/src/models.ts](../packages/ai/src/models.ts) | 944 | 「Spring 容器」：`createProvider()` 分发、认证解析、`calculateCost()` |
| 6 | [packages/ai/src/api/anthropic-messages.ts](../packages/ai/src/api/anthropic-messages.ts) L502–790 | — | 参考适配器：SSE → 统一事件，用量累计，流式 JSON 工具参数 |
| 7 | [packages/ai/src/api/transform-messages.ts](../packages/ai/src/api/transform-messages.ts) | 223 | 跨模型历史消息清洗。小文件，但沉淀了最多的血泪教训 |

**必须理解的几个硬核细节**

- **「永不抛异常」契约**：`stream()` 一旦被调用就不允许抛异常，所有失败都编码成 `error` 事件。这是因为异步流里的异常无处可抛。Java 里你会用 checked exception，这里用类型契约 + 纪律。
- **流式 JSON 修复**：工具参数是一个字符一个字符流回来的，中途都是残缺 JSON。`src/utils/json-parse.ts` 每来一个 delta 就尝试 `JSON.parse` → `repairJson` → 部分解析，所以 UI 能实时显示「正在调用 read(path: "src/ind...」。
- **没有真正的 tokenizer**：`src/utils/estimate.ts` 用「4 字符 ≈ 1 token」估算，真实数字来自厂商返回的 `usage` 字段。
- **两层重试**：HTTP 层（`utils/provider-retry.ts`，因为 SDK 自带的重试不响应 `AbortSignal`，只能自己重写）和消息层（`utils/retry.ts`，靠正则分类错误消息）。

**动手练习**
1. 用 `pi-ai` 写一个 50 行的终端聊天程序（流式输出）
2. 给它加一个工具（比如查天气的假实现），手动处理工具调用循环——**这一步会让你彻底明白 P3 要学什么**
3. 照着 `src/providers/faux.ts` 写一个自己的假 provider，返回预设脚本，不花钱

**验收标准**：能画出「一次 `models.stream()` 调用」从统一 `Context` 到 HTTP 请求、再从 SSE 回到统一事件流的完整数据流图。

### P3 — ★ Agent 循环：`packages/agent`（10–14 天）

**这是整条路线的核心阶段。** 前面是铺垫，后面是应用，真正的「Agent 工程」在这里。

**先动手，再读源码**（顺序很重要）

**练习 3.1（必做，最高价值）**：不看 Pi 的循环代码，只用 P2 学的 `pi-ai`，从零手写一个 agent。要求：
- 一个 `while` 循环
- 两个工具：`read_file`、`list_dir`
- 流式输出到终端
- 支持 Ctrl+C 取消

目标 200 行以内。写完之后再去读 [packages/agent/src/agent-loop.ts](../packages/agent/src/agent-loop.ts) 的 `runLoop()`，逐条对比：**它多做了什么，为什么？** 这个对比产生的理解，是任何教程都给不了的。

**你大概率会漏掉的（Pi 都做了）**：
- 模型因为 `length` 截断时，工具参数是残缺的，不能执行（`agent-loop.ts:211`）
- 工具并行执行，但预检要串行（保证钩子看到确定的顺序），结果又要按模型输出顺序回填（`executeToolCallsParallel` :489）
- 用户在模型思考时又输入了一句话（steering vs follow-up 两个队列）
- 工具抛异常不该终止循环，要转成 `isError` 的工具结果喂回给模型
- 取消信号要穿透到每一个工具的 `execute`

|---|---|---|---|
| 1 | [packages/agent/README.md](../packages/agent/README.md) | — | 事件时序图，先建立心智模型再看代码 |

**四个关键设计点**

1. **循环终止条件只有一个**：模型没返回工具调用（`agent-loop.ts:206`）。其他全是外围。
2. **`convertToLlm` 是必填钩子**。`AgentMessage` 可以包含 UI 专用的自定义消息类型（通过 TS 的**声明合并** `CustomAgentMessages` 扩展），但 LLM 只认 `user`/`assistant`/`toolResult`。每次请求前必须收窄回去。这是「应用模型 vs 传输模型」的经典分离。
3. **钩子体系**（`AgentLoopConfig` 上的函数属性）：`beforeToolCall`（可以拦截 → 这就是权限系统的挂载点）、`afterToolCall`、`shouldStopAfterTurn`、`prepareNextTurn`、`transformContext`。每一个的文档都写着「不得抛异常」，因为底层循环没有 try/catch 包着它们。
4. **`src/harness/**` 是下一代设计，还没实现完**。大部分操作会抛 `HarnessNotImplemented`。但它的设计文档 [packages/agent/docs/harness.md](../packages/agent/docs/harness.md) 是全项目最有价值的架构文档——会话树、崩溃恢复、不可变条目 + 追加日志。**这套东西你会觉得很熟：它就是事件溯源 + 状态机 + WAL。** 建议至少读 Part 0（Orientation）。

**验收标准**
- 手写的 agent 能跑通多轮工具调用
- 能说清楚 steering 队列和 follow-up 队列的区别，以及各自在循环的哪个位置排空
- 能解释「为什么工具并行执行但预检要串行」

**几个值得停下来想的设计**

- **系统提示词是组装的**：每个工具贡献自己的 `promptSnippet` 和 `promptGuidelines`；AGENTS.md / CLAUDE.md 作为 `<project_instructions>` 注入；技能列表作为 `<available_skills>` 追加。工具集变了，提示词会重建。
- **工具自带 UI**：`ToolDefinition` 里同时有 `execute` 和 `renderCall` / `renderResult`。领域逻辑和展示放在一起——跟 Spring 的分层直觉相反，值得想想为什么这里是对的。
- **工具的 IO 是可注入端口**：`read.ts` 定义了 `ReadOperations { readFile, access, ... }` 接口，默认绑到 `node:fs`。所以同一个工具可以跑在 SSH 上。这就是构造器注入，只是没有容器。
- **扩展系统用 jiti 运行时加载 `.ts`**：[src/core/extensions/loader.ts](../packages/coding-agent/src/core/extensions/loader.ts) 里的 `VIRTUAL_MODULES` 把依赖静态注入，好让单文件二进制里的扩展也能 import。**这个思路在 Java 里没有对应物**，值得专门研究。
- **没有内置权限系统**。README 明说了：要隔离就上容器。拦截点是 `tool_call` 事件返回 `{block: true}`，见 `examples/extensions/permission-gate.ts`。

**动手练习（三个由浅入深的扩展）**

参考 [packages/coding-agent/examples/extensions/](../packages/coding-agent/examples/extensions/)（约 80 个例子）：

1. **入门**：仿 `hello.ts`，写一个自定义工具（26 行就够）
2. **中级**：写一个斜杠命令 + 拦截 `tool_call` 做危险操作确认（参考 `commands.ts` + `confirm-destructive.ts`）
3. **进阶**：三选一 —— 自定义压缩策略（`custom-compaction.ts`）、自定义 provider（`custom-provider-anthropic/`）、子 agent（`subagent/`）

扩展放在 `.pi/extensions/*.ts` 就会被自动发现。注意本项目根目录的 [.pi/extensions/](../.pi/extensions/) 里就有 4 个真实在用的扩展，可以直接参考。

**验收标准**：能说清楚一次 `/compact` 从按下回车到会话文件被写入，经过了哪些模块。

## 五、Java → TypeScript 对照表

| Java / Spring | TypeScript / Pi | 关键差异 |
|---|---|---|
| `interface` + `implements` | `interface`（结构化类型） | 形状匹配即可赋值，不需要显式 `implements` |
| `sealed interface` + `record` + 模式匹配 | 可辨识联合 + `switch (x.type)` | TS 里用得更频繁随意。`AssistantMessageEvent` 是典型 |
| `Optional<T>` | `T \| undefined` + `?.` / `??` | 没有 Optional 类型，靠联合类型和空值合并 |
| Maven / Gradle 多模块 | npm workspaces | 见根 `package.json` 的 `workspaces` |
| `@Component` + DI 容器 | 显式传参 / options 对象 | **Pi 没有 DI 容器**。`createAgentSession({...})` 就是手动装配 |
| `@Autowired` 构造器注入 | `createReadTool(cwd, { operations })` | 同样的依赖倒置，只是没有框架帮你连线 |
| `CompletableFuture<T>` | `Promise<T>` + `async/await` | 单线程事件循环，没有线程池 |
| `Flux<T>` / 响应式流 | `AsyncIterable<T>` + `for await` | 见 `EventStream`，88 行手写的推拉队列 |
| `ExecutorService` | 无线程。`Promise.all` 是并发不是并行 | Node 单线程；CPU 密集要开 worker |
| `Thread.interrupt()` | `AbortSignal` / `AbortController` | 显式逐层传递。Pi 里 269 处 |
| `@Valid` + Bean Validation | TypeBox schema + `validateToolCall()` | 运行时校验必须显式写。schema 同时也发给大模型 |
| checked exception | 无。改用「永不抛异常」契约 + error 事件 | 见 `StreamFn` 的文档契约 |
| `Object` | `unknown`（安全）/ `any`（逃生舱） | 优先 `unknown` |
| static 工厂方法 | 导出函数 `createProvider()` | 模块即命名空间，不需要 class 包一层 |
| Spring 事件 / `@EventListener` | `agent.subscribe(fn)` | 监听器按注册顺序被 **await**，能当屏障用 |
| binlog / 事件溯源 | 追加式 JSONL 会话文件 + `reduceLaneState()` | 概念完全一致，你会读得很快 |
| 注解处理器 / 编译期生成 | 声明合并（`declare module`） | TS 独有：第三方可以往你的 interface 里加成员 |

## 六、需要补的 AI 基础（穿插在 P2/P3 里学，不用单独安排时间）

**必须懂**
- **Token 与上下文窗口**：为什么会「爆上下文」，为什么要压缩
- **计费模型**：input / output / cache read / cache write 四种价格，见 `calculateCost()`
- **工具调用（function calling）的真实协议**：你发 JSON Schema，模型回 JSON。仅此而已
- **系统提示词 vs 用户消息**：以及为什么系统提示词的位置影响缓存命中
- **流式（SSE）**：为什么必须流式（首字延迟）以及它带来的所有复杂度
- **提示词缓存**：`cache_control` 标记打在哪，能省多少钱
- **推理 / thinking 模型**：`ThinkingLevel`，思考 token 也要计费，跨模型传递要处理签名
- **停止原因（stop reason）**：`stop` / `length` / `toolUse` / `error` / `aborted`，每一个都要不同处理
- **上下文工程**：比「提示词工程」重要得多——放什么进上下文、什么时候丢

**现在可以先跳过**
- Transformer 内部结构、注意力机制
- 训练、微调、LoRA
- 向量数据库 / RAG（Pi 不用；它靠 grep 和 read，这本身就是个值得思考的设计选择）
- 多模态的细节

## 七、学习方法建议

1. **问题驱动，不要通读。** 每次带一个具体问题去读代码：「按 Ctrl+C 之后发生了什么？」比「读完 agent 包」有效十倍。
2. **写测试来理解。** `packages/agent/test/agent-loop.test.ts` 用 `MockAssistantStream` 做到零 API 调用测试 agent。学会这招，你就能安全地改任何东西。
3. **用 Pi 学 Pi。** 直接问它：「解释 `runLoop` 为什么要区分 steering 和 follow-up 队列」。它能读自己的源码。这也是项目 README 推荐的方式。
4. **每个阶段必须有代码产出。** 只读不写等于没学。
5. **善用 `git log -p <file>`。** 想知道某段奇怪的代码为什么存在，看它的提交历史和关联 issue 通常有答案。
6. **保持每天用 Pi 干活。** 用户视角和开发者视角互相强化。

**常见的坑**
- 别改 `packages/ai/src/models.generated.ts`（生成的）
- 别跑完整 vitest 套件，用 `./test.sh`
- 改完代码跑 `npm run check`（lint + 格式化 + 类型检查三合一）
- Node 需要 ≥ 22.19.0
