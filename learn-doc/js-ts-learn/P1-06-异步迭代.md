## 0. 一句话总结

**`Promise<T>` 是"一个将来的值",`AsyncIterable<T>` 是"一串将来的值"。**

| 数量 | 同步 | 异步 |
|---|---|---|
| 一个值 | `T` | `Promise<T>` |
| 多个值 | `Iterable<T>`(数组、Set) | **`AsyncIterable<T>`** |

Java 对照:

| JS | Java |
|---|---|
| `Iterable<T>` | `Iterable<T>` |
| `Promise<T>` | `CompletableFuture<T>` |
| `AsyncIterable<T>` | `Flux<T>` / `Publisher<T>`(响应式流) |
| `for await (const x of stream)` | `flux.subscribe(...)` 或 `StreamSupport` |

**但有个重要差别**:Java 的 `Flux` 来自 Reactor 这个大框架,自带调度器、背压、上百个操作符。**JS 的 `AsyncIterable` 是语言内建的,只有一个能力:一个一个地拿。** 轻是它的优点,也是它的局限。

Pi 全项目**没有引入任何响应式框架**,流式全靠这个语言原语 + 88 行的 `EventStream`。这是个很值得琢磨的取舍。

## 1. 先补基础:同步迭代器

`for...of` 能遍历什么?任何实现了 `Symbol.iterator` 的对象。

```ts
const arr = [1, 2, 3];
for (const x of arr) { }        // 数组内置了 Symbol.iterator
```

自己实现一个(电商:分页游标):

```ts
class OrderPage implements Iterable<Order> {
   private orders: Order[] = [...];

   [Symbol.iterator](): Iterator<Order> {
      let i = 0;
      const orders = this.orders;
      return {
         next(): IteratorResult<Order> {
            if (i < orders.length) {
               return { value: orders[i++], done: false };
            }
            return { value: undefined, done: true };
         },
      };
   }
}

for (const order of new OrderPage()) { }    // ✅ 能用了
```

`Symbol.iterator` 是个**计算属性名**——用 `[]` 包起来表示"用这个变量的值当属性名"。`Symbol` 是一种唯一的原始值,用它当 key 可以避免和普通字符串 key 冲突。

**协议本身就三样东西**:
- 对象有 `[Symbol.iterator]()` 方法
- 该方法返回一个有 `next()` 的对象
- `next()` 返回 `{ value, done }`

对应 Java 的 `Iterable` / `Iterator` / `hasNext()+next()`,只是 JS 把两件事合并成了一个返回值。

## 2. 生成器:让编译器帮你写迭代器

手写迭代器太啰嗦。`function*` 语法能自动生成:

```ts
function* orderIds(): Generator<string> {
   yield "O1001";
   yield "O1002";
   yield "O1003";
}

for (const id of orderIds()) { console.log(id); }
```

**`yield` 会"暂停"函数,把值吐出去,等下次 `next()` 再从这里继续。**

这是 Java 完全没有的能力(Java 只能用线程或者手写状态机模拟)。

**生成器是惰性的**——不调用就不执行:

```ts
function* infiniteIds(): Generator<number> {
   let i = 0;
   while (true) {                  // 无限循环!但不会卡死
      yield i++;
   }
}

for (const id of infiniteIds()) {
   if (id > 5) break;              // 取到就停
   console.log(id);
}
```

**电商场景:惰性分页**

```ts
function* chunk<T>(items: T[], size: number): Generator<T[]> {
   for (let i = 0; i < items.length; i += size) {
      yield items.slice(i, i + size);
   }
}

for (const batch of chunk(tenThousandOrders, 100)) {
   processBatch(batch);            // 一次只有 100 条在内存里
}
```

## 3. 异步版本:`AsyncIterable` 和 `for await`

把上面的东西全部加上 `async`:

| 同步 | 异步 |
|---|---|
| `Symbol.iterator` | `Symbol.asyncIterator` |
| `next(): IteratorResult<T>` | `next(): Promise<IteratorResult<T>>` |
| `function*` | `async function*` |
| `for...of` | `for await...of` |

**电商例子:分页拉取全部订单**

```ts
async function* fetchAllOrders(userId: string): AsyncGenerator<Order> {
   let cursor: string | undefined = undefined;

   do {
      const page = await api.getOrders(userId, cursor);   // 异步拿一页
      for (const order of page.items) {
         yield order;                                      // 一条一条吐出去
      }
      cursor = page.nextCursor;
   } while (cursor);
}

// 消费方完全感知不到分页的存在
for await (const order of fetchAllOrders("U888")) {
   console.log(order.id);
   if (order.amountCents > 100000) break;    // 提前退出,后面的页不会再请求
}
```

**这段代码的价值**:调用方看到的是"一个订单流",完全不需要关心分页、游标、网络。而且是**惰性**的——`break` 之后就不再发请求了。

Java 里要做同样的事,你得手写 `Iterator` + 内部缓冲,或者上 Reactor。

## 4. Pi 实战:逐行精读 `EventStream`

现在看 Pi 的核心原语。[packages/ai/src/utils/event-stream.ts](../packages/ai/src/utils/event-stream.ts) 全文 88 行,是整个项目最值得反复读的文件之一。

### 4.1 它要解决什么问题

LLM 的响应是**流式**的:服务端通过 SSE 一段一段推文本。Pi 需要:

- 把这些片段变成 `AssistantMessageEvent` 事件流
- 让消费方能 `for await` 逐个处理(实时显示打字效果)
- **同时**让消费方能直接 `await` 最终的完整消息(不关心过程的场景)
- 生产者(HTTP 解析)和消费者(UI)速度不一样,要能缓冲

**注意第三点**:同一个对象要支持两种消费方式。这是设计的关键。

### 4.2 完整源码

```ts
export class EventStream<T, R = T> implements AsyncIterable<T> {
   private queue: T[] = [];                                     // ① 缓冲区
   private waiting: ((value: IteratorResult<T>) => void)[] = []; // ② 等待中的消费者
   private done = false;
   private finalResultPromise: Promise<R>;
   private resolveFinalResult!: (result: R) => void;
   private isComplete: (event: T) => boolean;
   private extractResult: (event: T) => R;

   constructor(isComplete: (event: T) => boolean, extractResult: (event: T) => R) {
      this.isComplete = isComplete;
      this.extractResult = extractResult;
      this.finalResultPromise = new Promise((resolve) => {
         this.resolveFinalResult = resolve;                     // ③ deferred 模式
      });
   }

   push(event: T): void {
      if (this.done) return;

      if (this.isComplete(event)) {                             // ④ 判断是否终止事件
         this.done = true;
         this.resolveFinalResult(this.extractResult(event));
      }

      // Deliver to waiting consumer or queue it
      const waiter = this.waiting.shift();                      // ⑤ 有人在等吗?
      if (waiter) {
         waiter({ value: event, done: false });                 //    有 → 直接给他
      } else {
         this.queue.push(event);                                //    没有 → 先存着
      }
   }

   end(result?: R): void {
      this.done = true;
      if (result !== undefined) {
         this.resolveFinalResult(result);
      }
      while (this.waiting.length > 0) {                         // ⑥ 通知所有等待者:没了
         const waiter = this.waiting.shift()!;
         waiter({ value: undefined as any, done: true });
      }
   }

   async *[Symbol.asyncIterator](): AsyncIterator<T> {          // ⑦ 异步生成器方法
      while (true) {
         if (this.queue.length > 0) {
            yield this.queue.shift()!;                          //    队列里有 → 直接吐
         } else if (this.done) {
            return;                                             //    结束了 → 收工
         } else {
            const result = await new Promise<IteratorResult<T>>( //    等新事件
               (resolve) => this.waiting.push(resolve)
            );
            if (result.done) return;
            yield result.value;
         }
      }
   }

   result(): Promise<R> {
      return this.finalResultPromise;                           // ⑧ 另一种消费方式
   }
}
```

### 4.3 核心机制:推拉队列

这是个 **push/pull 队列**,两边速度不匹配时各自处理:

**情况 A:生产快于消费**(模型吐得比 UI 渲染快)

```
push(e1) → 没人在等 → queue = [e1]
push(e2) → 没人在等 → queue = [e1, e2]
消费者来了 → queue 非空 → 直接 shift 出 e1
```

**情况 B:消费快于生产**(UI 等着,模型还没吐)

```
消费者来了 → queue 空,done=false → 创建一个 Promise,把 resolve 存进 waiting
                                    → await 挂起,让出控制权
push(e1) → waiting 里有人 → 直接调他的 resolve(e1) → 消费者被唤醒
```

**⑤ 那三行是整个类的心脏**:

```ts
const waiter = this.waiting.shift();
if (waiter) waiter({ value: event, done: false });   // 直接交付,不经过队列
else this.queue.push(event);                         // 没人要,先囤着
```

Java 里这就是 `BlockingQueue`——但 `BlockingQueue.take()` 会**阻塞线程**,而这里 `await` 只是**挂起函数**,线程该干嘛干嘛(回忆 P1-02 §1)。

### 4.4 `async *[Symbol.asyncIterator]()` 拆解

这个方法签名信息量很大,拆成三部分:

- `async` —— 里面可以 `await`
- `*` —— 这是个生成器,可以 `yield`
- `[Symbol.asyncIterator]` —— 计算属性名,实现异步迭代协议

**合起来:一个异步生成器方法,让这个类能被 `for await` 遍历。**

方法体的 `while(true)` 循环有三条路径:

```ts
if (this.queue.length > 0)  yield this.queue.shift()!;   // 路径 1:有货,立刻给
else if (this.done)         return;                       // 路径 2:结束了,退出循环
else                        await ... ;                   // 路径 3:等着
```

**注意路径 1 和 3 的区别**:路径 1 不 `await`,所以连续消费队列里的积压事件时不会有额外延迟;只有真的没货了才挂起。

### 4.5 ⭐ 双消费模式:同一个对象两种用法

这是 `EventStream` 最巧妙的地方。

```ts
const stream = models.stream(model, context);

// 用法一:逐个消费(实时打字效果)
for await (const event of stream) {
   if (event.type === "text_delta") process.stdout.write(event.delta);
}

// 用法二:只要最终结果
const finalMessage = await stream.result();
```

**两者可以同时用**:

```ts
const stream = models.stream(model, context);

for await (const event of stream) {
   render(event);                          // 一边渲染
}
const message = await stream.result();     // 一边拿最终结果
```

`result()` 靠的就是 §4.2 ③ 那个 deferred 模式(P1-02 §6 讲过):构造时创建 Promise 并把 `resolve` 存起来,`push` 到终止事件时调用它。

`AssistantMessageEventStream` 就是把"什么算终止事件"填好的子类:

```ts
export class AssistantMessageEventStream extends EventStream<AssistantMessageEvent, AssistantMessage> {
   constructor() {
      super(
         (event) => event.type === "done" || event.type === "error",     // 什么算完
         (event) => {
            if (event.type === "done") return event.message;             // 怎么取结果
            else if (event.type === "error") return event.error;
            throw new Error("Unexpected event type for final result");
         },
      );
   }
}
```

**注意 `error` 也算"完成"**,返回的是 `event.error`(一个带 `stopReason: "error"` 的 `AssistantMessage`)。这就是 P1-02 §10.3 说的"永不抛异常"契约的实现——**失败不是异常,是一种正常的终止状态**。

所以 `await stream.result()` **永远不会 reject**,你不需要 try/catch,只需要检查 `message.stopReason`。

## 5. Pi 实战:消费侧长什么样

[packages/agent/src/agent-loop.ts:317](../packages/agent/src/agent-loop.ts#L317):

```ts
const response = await streamFunction(config.model, llmContext, { ...config, apiKey, signal });

let partialMessage: AssistantMessage | null = null;

for await (const event of response) {
   switch (event.type) {
      case "start":
         partialMessage = event.partial;
         context.messages.push(partialMessage);
         await emit({ type: "message_start", message: { ...partialMessage } });
         break;

      case "text_delta":
      case "thinking_delta":
      // ... 共九个流式事件
         if (partialMessage) {
            partialMessage = event.partial;
            context.messages[context.messages.length - 1] = partialMessage;
            await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
         }
         break;
      // done / error ...
   }
}
```

**三个值得注意的细节:**

**① 循环体里有 `await emit(...)`。** 事件处理器是异步的,而且被 `await` 了——这意味着**消费速度受订阅者影响**。如果 UI 渲染慢,`for await` 就慢,`EventStream` 的 `queue` 就会堆积。

这是**天然的背压**吗?**不完全是**——见 §6。

**② `{ ...partialMessage }` 每次都浅拷贝。** 因为 `event.partial` 是被**原地修改**的同一个对象(P2 会讲为什么这么设计),发给订阅者时要给个快照,否则订阅者存下来的引用会被后续事件改掉。

**③ 转发而非解释。** agent 层不理解 `text_delta` 和 `thinking_delta` 的语义差别,只是统一包成 `message_update` 转发出去。语义留给 UI 层。

## 6. ⚠️ 背压:`AsyncIterable` 的短板

**背压(backpressure)= 消费者跟不上生产者时的处理机制。**

Java 的 Reactive Streams 规范核心就是背压:消费者用 `request(n)` 告诉生产者"我只要 n 个",生产者不能多发。

**`AsyncIterable` 只有"弱背压"**:消费者不调 `next()`,生成器就不继续跑。

```ts
async function* slowProducer() {
   for (let i = 0; i < 1000; i++) {
      const data = await fetchPage(i);     // 消费者不要,这行就不执行
      yield data;
   }
}
```

**但 `EventStream` 是 push 模式**——数据由 HTTP 层主动 `push()` 进来,**消费快慢管不到生产者**:

```ts
push(event) {
   const waiter = this.waiting.shift();
   if (waiter) waiter({ value: event, done: false });
   else this.queue.push(event);              // ← 消费者慢?那就一直堆在这
}
```

**队列没有上限。** 如果模型疯狂输出而 UI 卡住,`queue` 会一直涨。

**Pi 为什么能接受这个?**

1. LLM 响应的总量是**有界**的(受 `maxTokens` 限制),最多几万个事件,内存扛得住
2. 真正的取消手段是 `AbortSignal`(P1-07),而不是背压——不想要了就直接掐断 HTTP 连接
3. 引入背压需要一整套协议,复杂度远超收益

**这是个典型的"知道代价后的简化"**。你在自己的项目里要判断:数据量是有界的吗?如果是无界流(日志、消息队列、传感器),就得考虑真正的背压方案。

## 7. 提前退出与清理

```ts
for await (const order of fetchAllOrders(userId)) {
   if (found) break;              // ← 提前退出
}
```

`break`(以及 `return`、`throw`)会调用迭代器的 `return()` 方法。**在生成器里,这相当于在当前 `yield` 处抛了一个特殊信号**,所以 `finally` 会执行:

```ts
async function* fetchWithCleanup() {
   const conn = await pool.acquire();
   try {
      while (true) {
         yield await conn.next();
      }
   } finally {
      await pool.release(conn);       // ✅ break 时也会执行
   }
}
```

**这是 `for await` 相比手动 `.subscribe()` 的一大优势:资源清理用 `try/finally` 就行,和同步代码一样自然。**

⚠️ **但 `EventStream` 没有实现 `return()`**。它的 `[Symbol.asyncIterator]` 是个异步生成器,`break` 会让生成器终止,但**底层的 HTTP 请求不会停**——`push()` 还会继续被调用,只是数据进了 `queue` 没人取。

**所以在 Pi 里想真正停止,必须用 `AbortSignal`,不能只靠 `break`。** 这是下一篇的主题。

## 8. 什么时候用什么

| 场景 | 用什么 |
|---|---|
| 一次拿到全部数据,量不大 | 普通数组 + `Promise<T[]>` |
| 一个异步结果 | `Promise<T>` |
| 有序的多个异步结果,量有界 | `AsyncIterable<T>` ✅ |
| 无界流 + 需要背压 | 专门的库(Node Streams / RxJS) |
| 需要复杂操作符(debounce、merge、retry) | RxJS |
| 多个订阅者(广播) | `AsyncIterable` **不行**,要用 EventEmitter 或 Observable |

**⚠️ 最后一条是个大坑**:`AsyncIterable` 是**单播**的。两个 `for await` 同时消费同一个 `EventStream`,事件会被**瓜分**而不是各自收到全部:

```ts
const stream = models.stream(...);
for await (const e of stream) { A(e); }     // ❌ 和下面抢
for await (const e of stream) { B(e); }     // ❌ 各拿到一半
```

Pi 怎么解决"多个订阅者"?**不用流,用回调**:

```ts
agent.subscribe((event) => { ... });      // 可以注册多个,每个都收到全部事件
```

**所以 Pi 里两套机制并存**:
- **`EventStream`** —— 单个消费者,一对一,用于 ai 层向 agent 层传流
- **`agent.subscribe()`** —— 多个订阅者,一对多,用于 agent 层向 UI/持久化/统计层广播

**理解这个分工很重要**,别指望用一种机制解决所有问题。

## 9. 常见坑速查

| 坑 | 症状 | 解法 |
|---|---|---|
| 用 `for...of` 遍历异步流 | 拿到 Promise 而不是值 | 用 `for await...of` |
| 多个消费者共享一个 AsyncIterable | 事件被瓜分 | 用回调订阅(`subscribe`)或先收集成数组 |
| 以为 `break` 能停止底层请求 | 请求还在跑,浪费资源/费用 | 用 `AbortSignal` |
| push 模式无背压导致内存涨 | 内存持续增长 | 确认数据有界;或加队列上限 |
| 忘了生成器是惰性的 | 函数体一行没执行 | 必须消费才会跑 |
| `for await` 里 `await` 慢操作 | 整个流被拖慢 | 想清楚是不是需要顺序处理 |
| 直接存 `event.partial` 引用 | 数据被后续事件改掉 | 存快照 `{ ...event.partial }` |
