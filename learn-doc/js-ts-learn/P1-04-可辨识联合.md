## 0. 一句话总结

**可辨识联合 = Java 的 `sealed interface`(17)+ `record`(16)+ `switch` 模式匹配(21)三件套,但更轻、更常用。**

```java
// Java 21(下面这个 switch 表达式的穷尽性检查需要 21;sealed 本身 17 就有了)
sealed interface Payment permits Alipay, WeChat, Card {}
record Alipay(String account) implements Payment {}
record WeChat(String openId) implements Payment {}
record Card(String no, String cvv) implements Payment {}

String describe(Payment p) {
    return switch (p) {
        case Alipay a -> "支付宝 " + a.account();
        case WeChat w -> "微信 " + w.openId();
        case Card c   -> "银行卡 " + c.no();
    };
}
```

```ts
// TypeScript —— 同一件事,少一半代码
type Payment =
   | { method: "alipay"; account: string }
   | { method: "wechat"; openId: string }
   | { method: "card"; no: string; cvv: string };

function describe(p: Payment): string {
   switch (p.method) {
      case "alipay": return `支付宝 ${p.account}`;
      case "wechat": return `微信 ${p.openId}`;
      case "card":   return `银行卡 ${p.no}`;
   }
}
```

**关键在于 `p.method` 这个字段**——它叫**判别字段(discriminant)**。TS 看到 `case "alipay"` 就知道"在这个分支里 `p` 一定是第一个成员",于是 `p.account` 可以访问,而 `p.openId` 会报错。

这个自动推断的过程叫**类型收窄(narrowing)**。

## 1. 从电商订单状态机入手

先看一个 Java 程序员的典型写法——**把所有字段塞进一个类,用可空字段区分**:

```ts
// ❌ 常见但糟糕的建模
interface Order {
   id: string;
   status: "pending" | "paid" | "shipped" | "cancelled";
   paidAt?: Date;             // 只有 paid 之后才有
   trackingNo?: string;       // 只有 shipped 才有
   cancelReason?: string;     // 只有 cancelled 才有
}

function render(order: Order) {
   if (order.status === "shipped") {
      console.log(order.trackingNo.toUpperCase());   // ❌ 报错:可能是 undefined
      console.log(order.trackingNo!.toUpperCase());  // 只能靠 ! 强行断言
   }
}
```

**问题**:类型没有表达"shipped 状态一定有 trackingNo"这个业务事实。编译器不知道,所以到处要 `!` 或者判空。而且 `{ status: "pending", trackingNo: "SF123" }` 这种非法状态也能构造出来。

**改成可辨识联合**:

```ts
// ✅ 让非法状态无法表示
type Order =
   | { status: "pending";   id: string; createdAt: Date }
   | { status: "paid";      id: string; createdAt: Date; paidAt: Date }
   | { status: "shipped";   id: string; createdAt: Date; paidAt: Date; trackingNo: string }
   | { status: "cancelled"; id: string; createdAt: Date; cancelReason: string };

function render(order: Order) {
   switch (order.status) {
      case "pending":
         return `待支付,下单于 ${order.createdAt}`;
      case "paid":
         return `已支付于 ${order.paidAt}`;              // ✅ paidAt 一定有
      case "shipped":
         return `运单号 ${order.trackingNo.toUpperCase()}`;  // ✅ 不需要 ! 了
      case "cancelled":
         return `已取消:${order.cancelReason}`;
   }
}
```

**收益**:
- `trackingNo` 在 `shipped` 分支里是 `string` 而不是 `string | undefined`,不需要任何断言
- 构造 `{ status: "shipped" }` 而不给 `trackingNo` 会**编译报错**
- 加新状态时,所有 switch 都会提醒你(见 §3)

**这就是"让非法状态无法表示"(make illegal states unrepresentable)**,是类型驱动设计的核心思想。Java 17 有了 sealed + record 之后也能这么建模,再配上 21 的 switch 模式匹配就完整了。

### 提取公共字段的两种写法

上面每个分支都重复写 `id` 和 `createdAt`,可以抽出来:

```ts
interface OrderBase {
   id: string;
   createdAt: Date;
}

type Order =
   | (OrderBase & { status: "pending" })
   | (OrderBase & { status: "paid";      paidAt: Date })
   | (OrderBase & { status: "shipped";   paidAt: Date; trackingNo: string })
   | (OrderBase & { status: "cancelled"; cancelReason: string });
```

Pi 里就是这么做的,看 [packages/agent/src/harness/session/types.ts:120](../packages/agent/src/harness/session/types.ts#L120):

```ts
export interface OperationFinishedRecord extends RecordBase {
   type: "operation_finished";
   runId: string;
   outcome: "completed" | "aborted" | "failed" | "declined";
   error?: { code: string; message: string };
}
```

`extends RecordBase` 提供公共字段(`id`、`seq`、`timestamp` 之类),`type` 是判别字段。

## 2. 判别字段的规则

判别字段必须是**字面量类型**(不能是 `string`):

```ts
// ✅ 可以判别
type A = { kind: "a"; x: number } | { kind: "b"; y: string };

// ❌ 无法判别:kind 是 string,TS 没法靠它区分
type B = { kind: string; x: number } | { kind: string; y: string };
```

字段名叫什么都行,常见的有 `type`、`kind`、`status`、`role`、`tag`。**Pi 统一用 `type`**,只有消息用 `role`(因为那是 LLM API 的约定):

```ts
// packages/ai/src/types.ts:409-455
export interface UserMessage       { role: "user";       content: ...; timestamp: number }
export interface AssistantMessage  { role: "assistant";  content: ...; usage: Usage; stopReason: StopReason; ... }
export interface ToolResultMessage { role: "toolResult"; toolCallId: string; toolName: string; isError: boolean; ... }

export type Message = UserMessage | AssistantMessage | ToolResultMessage;
```

**这三个类型就是整个 Pi 项目的地基**。P2 阶段你会天天见到它们。注意它们的字段差异非常大——`AssistantMessage` 有 `usage`、`stopReason`、`model` 等一堆,`UserMessage` 只有三个字段。用一个类根本没法表达。

## 3. ⭐ 穷尽性检查:加新分支时不会漏

这是可辨识联合**最大的实战价值**,一定要掌握。

场景:产品经理说订单要加个 `refunded` 状态。你在类型里加了一个分支:

```ts
type Order =
   | { status: "pending";   ... }
   | { status: "paid";      ... }
   | { status: "shipped";   ... }
   | { status: "cancelled"; ... }
   | { status: "refunded"; id: string; refundedAt: Date; amount: number };   // 新增
```

**项目里有 20 个地方 switch 了 order.status,怎么保证不漏?**

### 方法一:让函数有返回值类型

```ts
function render(order: Order): string {        // ← 标注返回类型
   switch (order.status) {
      case "pending":   return "待支付";
      case "paid":      return "已支付";
      case "shipped":   return "已发货";
      case "cancelled": return "已取消";
      // ❌ 报错:函数缺少结束 return 语句,返回类型不包括 undefined
   }
}
```

因为漏了 `refunded`,这个 switch 有条路径走不到任何 return,TS 立刻报错。

### 方法二:`never` 兜底(更明确,推荐)

```ts
function render(order: Order): string {
   switch (order.status) {
      case "pending":   return "待支付";
      case "paid":      return "已支付";
      case "shipped":   return "已发货";
      case "cancelled": return "已取消";
      default: {
         const _exhaustive: never = order;    // ❌ 报错:Order 不能赋给 never
         throw new Error(`未知状态: ${(order as any).status}`);
      }
   }
}
```

**原理**:如果所有分支都处理了,走到 `default` 时 `order` 的类型会被收窄成 `never`(不可能存在的类型),赋值给 `never` 合法。一旦漏了某个分支,`order` 在 default 里就是 `{status:"refunded",...}`,赋给 `never` 就报错。

**`never` 是"不可能"的类型**——没有任何值属于它。这是它最重要的用途。

**Pi 里的真实用法**,[packages/agent/src/proxy.ts:365](../packages/agent/src/proxy.ts#L365):

```ts
switch (proxyEvent.type) {
   // ... 处理 text_delta / toolcall_end / done / error 等等
   case "done":
      partial.stopReason = proxyEvent.reason;
      partial.usage = proxyEvent.usage;
      return { type: "done", reason: proxyEvent.reason, message: partial };

   case "error":
      partial.stopReason = proxyEvent.reason;
      partial.errorMessage = proxyEvent.errorMessage;
      partial.usage = proxyEvent.usage;
      return { type: "error", reason: proxyEvent.reason, error: partial };

   default: {
      const _exhaustiveCheck: never = proxyEvent;                        // ← 编译期保险
      console.warn(`Unhandled proxy event type: ${(proxyEvent as any).type}`);
      return undefined;                                                   // ← 运行时兜底
   }
}
```

**注意它同时做了两件事**:

- `const _exhaustiveCheck: never = proxyEvent` —— **编译期**保证不漏
- `console.warn(...) + return undefined` —— **运行时**兜底,因为数据来自网络,可能是新版本服务端发来的未知事件

**这个双保险很值得学**:类型系统只管你自己的代码,跨进程的数据永远要有运行时兜底。

对比 Java:`switch` on sealed interface 也有穷尽性检查,但你需要 Java 21+。而且 Java 的 switch 表达式必须有 `default` 或穷尽——机制类似,只是 TS 靠 `never` 这个"技巧"实现,不是语言内建。

## 4. 类型收窄的六种手段

`switch` 只是其中一种。完整清单:

```ts
type Value = string | number | Date | Order[] | null;

function handle(v: Value) {
   // ① typeof —— 原始类型
   if (typeof v === "string") { v.toUpperCase(); }
   if (typeof v === "number") { v.toFixed(2); }

   // ② instanceof —— class(运行时真实存在的)
   if (v instanceof Date) { v.getTime(); }

   // ③ Array.isArray
   if (Array.isArray(v)) { v.length; }

   // ④ 判空
   if (v == null) { return; }              // 同时排除 null 和 undefined
   if (v !== null) { }

   // ⑤ in 操作符 —— 判断字段存在(没有判别字段时用)
   type Res = { data: string } | { error: string };
   const r: Res = getRes();
   if ("error" in r) { r.error; } else { r.data; }

   // ⑥ 字面量比较 —— 就是判别字段那套
   // if (order.status === "paid") { ... }
}
```

### 自定义类型守卫(type predicate)

当上面六种都不够用时,自己写一个返回 `x is T` 的函数:

```ts
interface PaidOrder { status: "paid"; paidAt: Date; }

function isPaid(order: Order): order is PaidOrder {     // ← 返回类型是 `order is PaidOrder`
   return order.status === "paid";
}

const orders: Order[] = [...];
const paid = orders.filter(isPaid);      // 类型是 PaidOrder[],不是 Order[]!
```

**注意 `filter(isPaid)` 的威力**:普通的 `filter(o => o.status === "paid")` 返回 `Order[]`,而用类型守卫返回 `PaidOrder[]`。这在链式处理里非常有用。

Pi 里的真实例子,[packages/ai/src/models.ts:874](../packages/ai/src/models.ts#L874):

```ts
export function hasApi<TApi extends Api>(model: Model<Api>, api: TApi): model is Model<TApi> {
   return model.api === api;
}
```

用它就能从"任意 API 的模型"收窄到"确定是 anthropic-messages 的模型",从而访问该 API 特有的选项类型。

还有个更复杂的,[packages/ai/src/models.ts:393](../packages/ai/src/models.ts#L393):

```ts
(provider): provider is Provider & Required<Pick<Provider, "refreshModels">> =>
```

意思是"筛出那些**确实实现了 `refreshModels` 方法**的 provider",筛完之后调用就不用判空了。

以及 [packages/ai/src/api/lazy.ts:25](../packages/ai/src/api/lazy.ts#L25):

```ts
function hasResult(
   source: AsyncIterable<AssistantMessageEvent>,
): source is AsyncIterable<AssistantMessageEvent> & { result(): Promise<AssistantMessage> } {
   return typeof (source as { result?: unknown }).result === "function";
}
```

判断一个异步可迭代对象**有没有额外的 `result()` 方法**。这是结构化类型 + 类型守卫的组合拳:运行时用 `typeof === "function"` 探测,编译期用 `is` 告诉编译器结果。

⚠️ **类型守卫是"我保证"**,写错了编译器不会发现,运行时会崩。写的时候要保证 `return` 的逻辑真的验证了那个类型。

## 5. Pi 实战:12 个分支的流式事件

现在看 Pi 里最重要的一个联合类型,[packages/ai/src/types.ts:523](../packages/ai/src/types.ts#L523):

```ts
export type AssistantMessageEvent =
   | { type: "start";          partial: AssistantMessage }
   | { type: "text_start";     contentIndex: number; partial: AssistantMessage }
   | { type: "text_delta";     contentIndex: number; delta: string;  partial: AssistantMessage }
   | { type: "text_end";       contentIndex: number; content: string; partial: AssistantMessage }
   | { type: "thinking_start"; contentIndex: number; partial: AssistantMessage }
   | { type: "thinking_delta"; contentIndex: number; delta: string;  partial: AssistantMessage }
   | { type: "thinking_end";   contentIndex: number; content: string; partial: AssistantMessage }
   | { type: "toolcall_start"; contentIndex: number; partial: AssistantMessage }
   | { type: "toolcall_delta"; contentIndex: number; delta: string;  partial: AssistantMessage }
   | { type: "toolcall_end";   contentIndex: number; toolCall: ToolCall; partial: AssistantMessage }
   | { type: "done";  reason: Extract<StopReason, "stop" | "length" | "toolUse" | "deferred">; message: AssistantMessage }
   | { type: "error"; reason: Extract<StopReason, "aborted" | "error">; error: AssistantMessage };
```

**读这段要注意四件事:**

**① 有规律的三段式**:`xxx_start` → `xxx_delta`(多次)→ `xxx_end`,分别对应文本、思考、工具调用三种内容。理解了一组就理解了全部。

**② `partial` 字段每个分支都有**,它是"到目前为止累积的完整消息"。所以消费者既可以只处理增量(`delta`),也可以每次拿整体快照。

**③ 终止事件只有两个**:`done` 和 `error`。这呼应了 P1-02 讲的"永不抛异常"契约——失败不是异常,是一个 `error` 事件。

**④ `Extract<StopReason, ...>` 是从大联合里挑子集**。

先看 `StopReason` 的全集:

```ts
// packages/ai/src/types.ts:393
export type StopReason = "pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred";
```

`Extract<StopReason, "stop" | "length" | "toolUse" | "deferred">` 就是取交集,结果是那四个。这样类型系统就保证了:**`done` 事件的 reason 绝不可能是 `"error"`**。

**`Extract` 和 `Exclude` 是一对**:

```ts
type Success = Extract<StopReason, "stop" | "toolUse">;   // "stop" | "toolUse"
type NotError = Exclude<StopReason, "error" | "aborted">; // 除了这两个的其余全部
```

Java 里没有对应能力——你没法"从一个 enum 里取子集当新类型"。

### 消费侧长什么样

[packages/agent/src/agent-loop.ts:317](../packages/agent/src/agent-loop.ts#L317):

```ts
for await (const event of response) {
   switch (event.type) {
      case "start":
         partialMessage = event.partial;
         context.messages.push(partialMessage);
         await emit({ type: "message_start", message: { ...partialMessage } });
         break;

      case "text_start":
      case "text_delta":
      case "text_end":
      case "thinking_start":
      case "thinking_delta":
      case "thinking_end":
      case "toolcall_start":
      case "toolcall_delta":
      case "toolcall_end":
         // 九个分支共用一套逻辑:更新最后一条消息,发出 message_update
         if (partialMessage) {
            partialMessage = event.partial;
            context.messages[context.messages.length - 1] = partialMessage;
            await emit({ type: "message_update", assistantMessageEvent: event, message: { ...partialMessage } });
         }
         break;
      // ... done / error
   }
}
```

**注意 `case` 可以堆叠**(fall-through),九个事件共用一个处理块。这和 Java 的 switch 一样。

有意思的是:agent 层其实**不关心**是文本还是思考还是工具调用,它只负责"更新快照 + 广播"。真正区分这些的是 UI 层。**这是很好的分层——底层不解释语义,只搬运。**

## 6. 进阶:二级判别 + `?: never`

Pi 里有个更精妙的用法。看 [packages/agent/src/harness/session/types.ts:129](../packages/agent/src/harness/session/types.ts#L129):

```ts
export type StepAttemptRecord = RecordBase &
   (
      | {
            type: "step_attempt";
            runId: string;
            step: "assistant" | "branch_summary";
            attempt: number;
            resultEntryId: string;
            compactionReason?: never;              // ← 注意这里
        }
      | {
            type: "step_attempt";
            runId: string;
            step: "compaction";
            attempt: number;
            resultEntryId: string;
            /** Persists why compaction summary generation started so recovery resumes the same work. */
            compactionReason: CompactionReason;    // ← 这里是必填
        }
   );
```

**看出门道了吗?** 两个分支的 `type` 是**一样的**(都是 `"step_attempt"`),真正的判别字段是**第二层的 `step`**。

业务含义:
- `step` 是 `assistant` 或 `branch_summary` 时,**不允许**有 `compactionReason`
- `step` 是 `compaction` 时,**必须**有 `compactionReason`

`compactionReason?: never` 的意思是:"这个字段是可选的,但它的类型是 `never`——没有任何值能赋给它,所以你只能不写它(即 `undefined`)"。

**这是表达"互斥字段"的标准技巧。** 效果:

```ts
const r1: StepAttemptRecord = { type: "step_attempt", step: "assistant", compactionReason: "manual", ... };
// ❌ 报错:两个分支都匹配不上
//    第一个分支要求 compactionReason 是 never(即只能不写),给了 "manual" 不符;
//    第二个分支要求 step 是 "compaction",给了 "assistant" 也不符

const r2: StepAttemptRecord = { type: "step_attempt", step: "compaction", ... };
// ❌ 报错:缺少 compactionReason

const r3: StepAttemptRecord = { type: "step_attempt", step: "compaction", compactionReason: "threshold", ... };
// ✅
```

同一个文件里 `QueueEnqueuedRecord` 也用了这招(`runId?: never`)。

**为什么要这么较真?** 因为这些 record 是**崩溃恢复日志**——重启后要靠它们重建状态。如果一条 `compaction` 记录缺了 `compactionReason`,恢复时就不知道该继续做什么。**类型系统在这里承担了数据完整性约束的职责**,相当于数据库的 CHECK 约束,只不过是编译期的。

## 7. 为什么 Pi 不用继承和多态?

Java 程序员的第一反应可能是:这些事件为什么不做成一个抽象类 + 12 个子类?

```java
// Java 风格
abstract class Event { }
class TextDeltaEvent extends Event { String delta; }
class DoneEvent extends Event { AssistantMessage message; }
// ... 然后靠多态 dispatch
```

**Pi 选联合类型有五个理由:**

**① 数据要能被 JSON 序列化。** 事件要写进会话文件、要跨进程传(RPC 模式)、要发到远程。class 实例序列化后就丢了原型链,反序列化还得写工厂方法。**纯对象天生可序列化。**

Pi 甚至有个函数专门检查这一点——`assertJsonSerializable`([session/session.ts:42](../packages/agent/src/harness/session/session.ts#L42)),它会拒绝循环引用、非普通对象、访问器属性。

**② 行为不属于数据。** 一个 `text_delta` 事件在 UI 层要渲染,在持久化层要序列化,在统计层要计数。**用多态的话这些行为都得塞进事件类里**,导致事件类依赖 UI、依赖存储。用联合类型,行为放在各自的 switch 里,数据保持纯净。

这其实是**表达式问题(expression problem)**的经典权衡:
- **继承/多态**:容易加新类型(加个子类就行),难加新操作(要改所有子类)
- **联合类型 + switch**:难加新类型(要改所有 switch),容易加新操作(写个新函数)

Pi 的事件类型很少变,但消费方式非常多样(TUI、JSON 模式、RPC、扩展、telemetry),所以选联合类型是对的。

**③ 穷尽性检查更强。** 加了新事件类型,所有 switch 都编译报错。用多态的话,漏实现一个子类的方法可能到运行时才发现(或者被基类默认实现悄悄吞掉)。

**④ 更轻。** 12 个 class 是 12 个运行时对象;12 个联合分支编译后什么都不剩。

**⑤ Pi 的硬约束。** `erasableSyntaxOnly` 禁止了 `enum` 等语法,项目整体偏向"数据 + 函数"而非"对象 + 方法"。

**判断标准**:如果你的类型集合**基本固定、但操作会不断增加**(事件、消息、AST 节点、状态机状态)→ 用联合类型。如果**类型会不断增加、操作相对固定**(插件、策略、handler)→ 用接口 + 实现(Pi 的工具就是这样,见 P1-03)。

## 8. 常见坑速查

| 坑 | 症状 | 解法 |
|---|---|---|
| 判别字段类型是 `string` | 收窄不生效,访问字段报错 | 必须是字面量类型;必要时加 `as const` |
| 忘了穷尽性检查 | 加新分支后漏改,运行时才发现 | 标注返回类型,或加 `never` 兜底 |
| 用 `if/else if` 链而不是 switch | 没有穷尽性检查 | 优先用 switch;必须用 if 就在最后加 never 断言 |
| 类型守卫写错 | 编译通过,运行时崩 | 确保 return 的判断逻辑真的验证了那个类型 |
| 直接访问非公共字段 | "属性不存在于类型 X 上" | 先收窄再访问 |
| 跨进程数据只靠类型 | 收到未知类型直接崩 | 编译期 `never` + 运行时兜底(学 proxy.ts) |
| 联合分支太多难维护 | switch 几百行 | 抽公共 base;或者考虑是不是该用接口了 |
