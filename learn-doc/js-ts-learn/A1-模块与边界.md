## 本章要回答的唯一问题

> **在 TS 项目里,"一个包对外暴露什么"这件事,写在哪儿?**

Java 的答案你闭着眼都能说：`public` 修饰符 + package 结构 + （Java 9 之后）`module-info.java`。三层,编译器全程强制。

TS 的答案是**三个不同的文件,而且没有一个是编译器强制的**：

| 文件 | 管什么 | Java 对应 |
|---|---|---|
| `package.json` 的 `exports` | 外部能 import 到哪些路径 | `module-info.java` 的 `exports` |
| `src/index.ts` | 主入口具体导出哪些符号 | 一个 Facade 类 |
| `tsconfig.json` 的 `paths` | 开发期（monorepo 内部）怎么解析 | Maven 本地仓库 + `<dependency>` |

本章按"文件 → 包 → 仓库"三级往上走,每一级都用同一个电商例子贯穿。

**贯穿全文的例子**：一个订单系统,拆成四个包。

```
order-core          领域模型：Order / OrderItem / Money，纯类型，零依赖
order-pricing       计价：优惠券、满减、税费
order-service       下单流程：校验 → 计价 → 扣库存 → 落库
order-sdk           给外部团队用的客户端 SDK（浏览器 + Node 都要能跑）
```

Spring 里这是四个 Maven 模块。下面看 TS 里怎么表达。

## 第 1 节 · 模块的最小单位：文件

### 1.1 文件即模块,路径即身份

Java 里模块身份是**声明出来的**：

```java
// src/main/java/com/shop/order/Money.java
package com.shop.order;   // ← 这一行决定了它的身份
public record Money(long cents, String currency) {}
```

目录必须和 `package` 一致,但**身份来自那行声明**。

TS 里没有 package 声明。**文件路径本身就是模块 ID**：

```ts
// packages/order-core/src/money.ts
export interface Money {
   cents: number;
   currency: "CNY" | "USD";
}

export function yuan(amount: number): Money {
   return { cents: Math.round(amount * 100), currency: "CNY" };
}
```

别人怎么用它：

```ts
import { yuan, type Money } from "./money.ts";
```

注意三点：

1. **没有 `package` 声明**,也没有 classpath。`./money.ts` 是相对当前文件的物理路径。
2. **Pi 写显式 `.ts` 后缀**。这是 Node 原生"类型剥离"模式的要求 —— Node 直接跑 `.ts` 文件,不经过编译,所以导入路径必须指向真实存在的文件。很多老项目写 `.js` 或不写后缀,Pi 有个脚本专门禁止（见 6.4）。
3. **一个文件可以导出任意多个东西**,不像 Java 一个 `public` 类必须一个文件。

> **Java 工程师最容易懵的一点**：TS 里没有"包私有"。一个符号只有两种状态 —— `export` 了（谁都能 import）或者没 `export`（只有本文件能用）。**中间没有 `protected` / package-private 这一档。** 想表达"包内可见",只能靠目录约定 + 不在 `index.ts` 里导出（见第 4 节）。

### 1.2 三种导出形态,Pi 只用一种

```ts
// ① 命名导出 —— Pi 全项目只用这个
export function yuan(a: number): Money { ... }
export interface Money { ... }

// ② 默认导出 —— Pi 全项目仅 2 处（且都是外部框架要求的形态：插件入口、vitest reporter）
export default function yuan(a: number) { ... }

// ③ 重导出（re-export）—— barrel 文件专用，见第 4 节
export * from "./money.ts";
export { yuan } from "./money.ts";
```

**为什么 Pi 只用命名导出**,三个理由：

- **可搜索**：`grep "yuan"` 能同时找到定义和所有使用点。默认导出可以在导入处随便改名（`import 随便什么 from "./money.ts"`）,搜不到。
- **重命名安全**：IDE 重命名能全局生效。
- **tree-shaking 友好**：打包器能精确知道你用了哪几个符号,没用的删掉。这对 `coding-agent` 这种要打成单文件 CLI 的场景很关键。

**建议你直接照抄这条规矩**：永远命名导出。这是 TS 社区近几年基本形成的共识。

### 1.3 模块是单例 —— 你的 `@Component` 已经在这了

这条是理解"为什么 TS 不需要 IoC 容器"的第一块砖。

**同一个模块路径,无论被 import 多少次,顶层代码只执行一次,导出的对象是同一个引用。**

电商例子 —— 汇率缓存：

```ts
// packages/order-pricing/src/fx-rate.ts
const cache = new Map<string, number>();     // ← 模块顶层，整个进程只有这一份

export function getRate(from: string, to: string): number {
   const key = `${from}->${to}`;
   const hit = cache.get(key);
   if (hit !== undefined) return hit;
   const rate = fetchRateSync(from, to);
   cache.set(key, rate);
   return rate;
}
```

Spring 里等价物：

```java
@Component                                    // 默认 singleton scope
public class FxRateCache {
    private final Map<String, Double> cache = new ConcurrentHashMap<>();
    public double getRate(String from, String to) { ... }
}
```

然后你要 `@Autowired FxRateCache fxRateCache;`。

**TS 版本里,`import { getRate } from "./fx-rate.ts"` 就完事了。** 不需要容器,因为 ES 模块规范本身就保证了单例语义 —— 模块被解析、执行、缓存,后续所有 import 拿到的是同一个模块记录。

注意 `new Map()` **不是** `ConcurrentHashMap`。因为 Node 单线程,不存在并发写入,普通 `Map` 就够了（回到 A0 第 5 条）。

> **代价**：模块级单例是"隐式"的,你没法像 Spring 那样换个 scope、换个实现、或者在测试里注入一个 mock。所以 Pi 里真正需要替换的东西（telemetry、streamFn、session 存储）**都不是模块级单例,而是通过参数传进去的**（A3 会详讲）。**模块单例只用在"确实全局唯一且不需要替换"的东西上**,比如注册表、常量表。

### 1.4 副作用与"side-effect free"

模块顶层代码在第一次 import 时执行。如果顶层干了重活,import 它就有代价：

```ts
// ❌ 有副作用的模块
import { readFileSync } from "node:fs";
export const COUPON_TABLE = JSON.parse(readFileSync("./coupons.json", "utf8"));
//                          ↑ 只要有人 import 这个文件，就会读磁盘
```

Java 类比：`static {}` 初始化块。区别是 Java 的静态初始化是懒的（首次主动使用才触发）,而 **ES 模块是急切的** —— import 语句一执行,整条依赖链的顶层代码全跑一遍。

**Pi 对这件事非常在意**。看 [packages/ai/src/index.ts](../../packages/ai/src/index.ts) 顶部的真实注释：

```ts
// Core only, side-effect free: no generated catalogs, no provider factories,
// no api-registry, no OAuth implementations, no compat. Provider factories
// live under "@earendil-works/pi-ai/providers/*", API implementations under
// "@earendil-works/pi-ai/api/*", the old global API under
// "@earendil-works/pi-ai/compat".
```

翻译：**主入口只放类型和轻量工具,凡是"一 import 就会加载几十个 provider 定义 / 几 MB 模型目录"的东西,全部挪到 subpath 入口去。**

这直接决定了 `packages/ai/src/index.ts` 只有 47 行。它是一个刻意做窄的门。

**Spring 类比**：相当于你刻意不让 `order-core` 模块引入任何 `@Configuration`,保证别人依赖它时不会意外拉起一堆 Bean。只不过 Spring 里这是靠"不加注解"实现的,TS 里是靠"不在 index.ts 里导出重的东西"实现的。

## 第 2 节 · `import type`：切断运行时依赖的手术刀

这是 Java 完全没有的概念,但对理解 TS 架构极其重要。

### 2.1 两种依赖

```ts
// packages/order-service/src/place-order.ts
import { chargePayment } from "../../payment/src/gateway.ts";   // ① 运行时依赖：我要调它
import type { PaymentResult } from "../../payment/src/types.ts"; // ② 类型依赖：我只要它的形状
```

- **①** 编译后仍然存在,运行时真的会去加载那个模块。
- **②** **编译后完全消失**。`tsc` 把这一行直接删掉,产物里没有任何痕迹。

电商场景下的典型用法：

```ts
// packages/order-service/src/types.ts
import type { Money } from "@shop/order-core";
import type { PaymentResult } from "@shop/payment";

export interface PlaceOrderResult {
   orderId: string;
   total: Money;               // 只是用来描述形状
   payment: PaymentResult;     // 只是用来描述形状
}
```

这个文件编译后是**空文件**。它不产生任何运行时依赖,`order-service` 的运行时不会因为这个文件而加载 `payment` 模块。

Java 里没有对应物：`import com.shop.payment.PaymentResult;` 就是实打实的编译期 + 运行时依赖,`payment` 的 jar 必须在 classpath 上。

### 2.2 Pi 里的实际比例

```
import type ...     508 处
import { ... }     1511 处
```

四分之一的导入是纯类型导入。这不是洁癖 —— 它有三个实打实的收益。

### 2.3 三个收益

**① 破循环依赖。** 电商里最经典的循环：

```
order  需要知道 payment 的结果类型
payment 需要知道 order 的 ID 类型
```

Java 里遇到这个,你只能拆出第三个模块 `order-payment-api` 放公共类型。TS 里如果两边都是**纯类型**引用,直接 `import type` 就行 —— 因为运行时根本没有这条边,循环不存在。

（如果是运行时循环依赖,TS 一样会炸,而且报错很难看。所以这个技巧只对类型有效。）

**② 让"可选依赖"成立。** `order-sdk` 想在类型上引用 Node 的 `Buffer`,但运行时要能在浏览器跑 —— `import type` 就能做到"类型上知道,运行时不加载"。

**③ 让编译器能安全地只做转译。** Node 原生跑 `.ts` 时是"删掉类型直接跑",它必须能逐文件判断哪些 import 该删。`import type` 是给它的明确信号。

> **读源码时的实用技巧**：想看一个文件的**真实运行时依赖**,只数 `import {`,跳过 `import type`。想看它的**概念依赖**,两个都数。Pi 里这两张图差别很大。

## 第 3 节 · 包的正门：`package.json`

从文件级上升到包级。

### 3.1 先看一个最小的电商包

```json
{
  "name": "@shop/order-core",
  "version": "1.4.0",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
  },
  "files": ["dist", "README.md"],
  "dependencies": {}
}
```

逐字段对照 `pom.xml`：

| package.json | pom.xml | 说明 |
|---|---|---|
| `name` | `groupId` + `artifactId` | `@shop/` 是 scope,类似 groupId |
| `version` | `version` | |
| `type: "module"` | 无 | 声明用 ESM 而非老的 CommonJS。Pi 全线 `"type": "module"` |
| `exports` | `module-info.java` 的 `exports` | **可见性边界** |
| `files` | `<includes>` / jar 打包配置 | 发布到 npm 时**只有这些文件进包**,`src` 不进 |
| `dependencies` | `<dependencies>` compile scope | |
| `devDependencies` | `<scope>test</scope>` / `provided` | 不会传递给使用者 |

### 3.2 `exports` 才是边界（重点）

老写法是 `"main": "./dist/index.js"` —— 只是**指定默认入口**,不限制别的。使用者照样能 `import "@shop/order-core/dist/internal/secret.js"`,把你的内部实现扒出来用。这就是 JS 生态过去二十年"没有封装"的根源。

现代写法 `exports` 是**白名单**：**没列出来的路径,外部一律 import 不到,运行时直接报错。**

看 Pi 的真实例子,[packages/agent/package.json](../../packages/agent/package.json)：

```json
"exports": {
  ".":                  { "types": "./dist/index.d.ts", "import": "./dist/index.js" },
  "./node":             { "types": "./dist/node.d.ts",  "import": "./dist/node.js" },
  "./session/testing":  { "types": "./dist/harness/session/testing/index.d.ts",
                          "import": "./dist/harness/session/testing/index.js" },
  "./package.json":     "./package.json"
}
```

**四个入口,四种意图**：

| 入口 | 谁用 | Java 类比 |
|---|---|---|
| `.` | 所有人,跨运行时可用 | 主 API |
| `./node` | 只在 Node 里跑的使用者 | 一个 `-jre` classifier 的 jar |
| `./session/testing` | 写测试的人 | `test-jar` |
| `./package.json` | 工具链读元信息 | 读 pom |

`dist` 里其他所有文件 —— 那 12,635 行源码编译出来的几百个 `.js` —— **外部一个都碰不到**。

回到电商例子,`order-sdk` 该开哪些门：

```json
{
  "name": "@shop/order-sdk",
  "exports": {
    ".":          { "types": "./dist/index.d.ts",        "import": "./dist/index.js" },
    "./node":     { "types": "./dist/node.d.ts",         "import": "./dist/node.js" },
    "./testing":  { "types": "./dist/testing/index.d.ts", "import": "./dist/testing/index.js" }
  }
}
```

- `.` —— 纯 fetch 实现,浏览器也能跑
- `./node` —— 带文件上传、带 keep-alive 连接池,依赖 `node:fs`
- `./testing` —— 一个内存版 mock server,给使用方写单测

**"按运行环境切入口"是 JS 生态特有的架构手段。** Java 里一份 jar 到处跑,不需要这个。JS 里同一份代码要跑在 Node / 浏览器 / Bun / Deno / Edge Runtime 上,能力集完全不同,所以必须在**包的入口层面**就切开。

看 [packages/agent/src/node.ts](../../packages/agent/src/node.ts) 这个文件,总共两行：

```ts
export { NodeExecutionEnv } from "./harness/env/nodejs.ts";
export * from "./index.ts";
```

**读法**：`./node` 入口 = 主入口的全部 + 一个 Node 专属的执行环境实现。反过来说,主入口 `.` 里**绝不能出现任何 `node:` 开头的 import**,否则浏览器打包直接炸。这个约束怎么强制?见 6.3。

### 3.3 通配入口：让整个目录成为公开 API

[packages/ai/package.json](../../packages/ai/package.json)：

```json
"exports": {
  ".":                  { ... },
  "./compat":           { ... },
  "./providers/*":      { "types": "./dist/providers/*.d.ts", "import": "./dist/providers/*.js" },
  "./api/*":            { "types": "./dist/api/*.d.ts",       "import": "./dist/api/*.js" },
  "./oauth":            { ... },
  "./bedrock-provider": { ... },
  "./bun-oauth":        { ... }
}
```

`./providers/*` 的意思是：**`providers` 目录整体对外开放,按需引哪个引哪个。**

为什么这么设计?回到 1.4 的"side-effect free"。`ai` 包支持 40+ 个 provider,如果全塞进主入口,任何人 import 这个包就得加载全部 40 个的定义 + 模型目录 JSON。开成通配入口后:

```ts
import { anthropic } from "@earendil-works/pi-ai/providers/anthropic";   // 只加载这一个
```

**电商类比**：你的 `@shop/payment` 支持支付宝、微信、银联、Stripe、PayPal 五个渠道,每个都带自己的 SDK 依赖。开成 `"./channels/*"`,用户只用支付宝时,微信和 Stripe 的 SDK 根本不会被加载。

Java 里对应做法是**拆成五个 artifact**（`payment-alipay`、`payment-wechat`…）。TS 里可以在**一个包内部**用 subpath 达到同样效果 —— 这是 exports 机制比 Maven 灵活的地方。

### 3.4 `bin`：CLI 入口

```json
// packages/coding-agent/package.json
"bin": { "pi": "dist/cli.js" }
```

`npm i -g` 之后,`pi` 命令就能用了。等价于 Spring Boot 的 `spring-boot-maven-plugin` 打出可执行 jar + 一个 shell 包装。

### 3.5 `files`：什么进 npm 包

```json
"files": ["dist", "docs", "examples", "containerization.md", "CHANGELOG.md", "npm-shrinkwrap.json"]
```

**注意 `src` 不在里面。** 发布出去的包里没有 TS 源码,只有编译产物。但因为 tsconfig 开了 `declarationMap` + `inlineSources`,使用者在 IDE 里"跳转到定义"仍然能看到原始 TS 代码 —— source map 里内嵌了源码。

Java 类比：只发 jar 不发 sources.jar,但把行号表和源码塞进了 jar 里。

### 3.6 小结：判断一个包"想被怎么用"

拿到任何 TS 包,先看这四个字段,三十秒得出结论：

| 看什么 | 说明什么 |
|---|---|
| `exports` 的**入口数量和形状** | 暴露面有多宽,有没有按环境切分 |
| `dependencies` 的**数量和内容** | 是纯库还是重框架 |
| `files` | 发布产物包含什么 |
| `bin` | 是不是命令行工具 |

## 第 4 节 · 门面文件 `index.ts`

`exports` 决定了"外部能访问哪些**路径**",`index.ts` 决定了主入口这个路径上"具体有哪些**符号**"。

### 4.1 什么是 barrel

一个只做重导出、自己没有逻辑的文件：

```ts
// packages/order-core/src/index.ts
export * from "./money.ts";
export * from "./order.ts";
export type { OrderStatus } from "./status.ts";
```

使用者：

```ts
import { yuan, type Order, type OrderStatus } from "@shop/order-core";
```

Java 类比：一个只有 `public static` 重导出的 Facade 类,加上 `package-info.java` 的作用。Java 里其实不太需要这东西（因为有 package + public 两级可见性）,TS 里它是**表达"哪些是公开 API"的唯一手段**。

### 4.2 行数就是架构信号

```
telemetry/src/index.ts      357 行   接口直接定义在这（它整个包就是一份契约）
coding-agent/src/index.ts   408 行   产品层，什么都要暴露
tui/src/index.ts            147 行
agent/src/index.ts          145 行
ai/src/index.ts              47 行   ★ 刻意做窄
protocol/src/index.ts         4 行   只有四条 export *
```

`ai` 是两万三千行的包,主入口只有 47 行；`coding-agent` 是五万九千行的包,主入口 408 行。**这个对比本身就告诉你哪个包是"给人用的库",哪个是"什么都往外倒的产品层"。**

### 4.3 逐行拆解 `ai/src/index.ts`

这 47 行值得精读,它把三种重导出手法全用上了：

```ts
export type { Static, TSchema } from "typebox";     // ① 转发第三方类型
export { Type } from "typebox";                     // ② 转发第三方值

export type { AnthropicOptions, ... } from "./api/anthropic-messages.ts";   // ③ 只导出类型，不导出实现
export * from "./api/lazy.ts";                                             // ④ 整个文件全导出
export * from "./types.ts";
export { contentText } from "./utils/text.ts";                             // ⑤ 只挑一个符号
export { uuidv7 } from "./utils/uuid.ts";
```

**关键在于 ③ 和 ⑤ 这两种"挑着导出"**：

- ③ `export type { AnthropicOptions } from "./api/anthropic-messages.ts"` —— 只把**类型**转发出去,那个文件里的实现代码一行都不进主入口。使用者能写 `const opts: AnthropicOptions = {...}`,但拿不到 Anthropic 的实现,想要实现得走 `@earendil-works/pi-ai/api/anthropic-messages` 这个 subpath。
- ⑤ `export { contentText }` —— 那个 `utils/text.ts` 里可能有二十个函数,只有一个被认为是公开 API。

**这就是 TS 里"包私有"的实现方式**：文件里 `export` 了,但 barrel 不转发 → 包内其他文件能 `import { helper } from "./utils/text.ts"` 用它,包外没门。

**电商版本**：

```ts
// packages/order-pricing/src/index.ts

// 公开 API：只有这三个
export { calculateTotal } from "./calculator.ts";
export { applyCoupon } from "./coupon.ts";
export type { PricingResult, PricingBreakdown } from "./types.ts";

// 内部实现，故意不导出：
//   ./tax-table.ts        —— 税率表，会变，不想承诺兼容性
//   ./rounding.ts         —— 四舍五入策略，内部细节
//   ./calculator.ts 里的 normalizeItems() 等十几个辅助函数
```

对照 Spring：这相当于把 `TaxTable` 和 `RoundingStrategy` 声明为 package-private,只留 `PricingService` 是 public。**只不过 Java 编译器会强制,TS 靠的是"我不在 barrel 里写它"。**

### 4.4 barrel 的两个坑

**坑 1：循环依赖。** 包内文件之间互相 import barrel,极易成环：

```ts
// ❌ calculator.ts
import { applyCoupon } from "./index.ts";     // 从 barrel 反向引用
```

**规矩：包内文件永远用相对路径直接引具体文件,只有包外才走 barrel。** Pi 全程遵守这条。

**坑 2：`export *` 会拖累 tree-shaking。** 如果 barrel 里 `export * from "./heavy.ts"`,而 `heavy.ts` 有顶层副作用,那么任何人 import 这个包都会触发它。这就是 1.4 里 `ai` 包那段注释的由来。

**规矩：barrel 里对"重"的模块用具名导出,对纯类型模块才敢 `export *`。**

### 4.5 分层 barrel：两行文件的智慧

再看一次 [packages/agent/src/node.ts](../../packages/agent/src/node.ts)：

```ts
export { NodeExecutionEnv } from "./harness/env/nodejs.ts";
export * from "./index.ts";
```

这两行表达了一个完整的分层决策：

```
index.ts   ─── 跨运行时安全的部分（浏览器、Bun、Node 都能用）
   ↑
node.ts    ─── index.ts 的全部 + Node 独有能力
```

使用者按自己的环境挑入口,**而且挑错了会在打包时立刻炸**（因为浏览器打包器解析不了 `node:fs`）。

**电商版本**：

```ts
// packages/order-sdk/src/index.ts —— 浏览器安全
export { createOrderClient } from "./client.ts";      // 内部只用 fetch
export type * from "./types.ts";

// packages/order-sdk/src/node.ts —— Node 专用
export { createOrderClientWithProxy } from "./node-client.ts";   // 用 node:https 走公司代理
export { uploadInvoicePdf } from "./node-upload.ts";             // 用 node:fs 读本地文件
export * from "./index.ts";
```

Java 里你没有这个问题,所以也没有这个概念。**但在 TS 里,"这个包能在哪儿跑"是包设计的第一等约束,和"这个包干什么"同等重要。**

## 第 5 节 · Monorepo：workspaces + tsconfig paths

从包级上升到仓库级。

### 5.1 workspaces = Maven `<modules>`

```json
// 根 package.json
{
  "name": "pi-monorepo",
  "private": true,
  "workspaces": [
    "packages/*",
    "packages/session-backends/*",
    "packages/coding-agent/examples/extensions/with-deps",
    ...
  ]
}
```

对照：

```xml
<modules>
    <module>order-core</module>
    <module>order-pricing</module>
    <module>order-service</module>
    <module>order-sdk</module>
</modules>
```

`private: true` = 这个根包本身不发布（等价于 Maven 的 `<packaging>pom</packaging>` 聚合模块）。

注意 `"packages/session-backends/*"` 单独列了一行 —— 因为 `packages/*` 只匹配一层。`session-backends` 是个**容器目录**,里面装着 `sqlite-node` 一个包。这种"预留分组"说明作者打算以后加 Postgres 等后端。

### 5.2 依赖解析：符号链接 vs 本地仓库

`npm install` 时,workspace 内的包**互相之间建符号链接**：

```
node_modules/@earendil-works/pi-ai  ->  ../../packages/ai      （软链）
```

所以 `agent` 里 `import ... from "@earendil-works/pi-ai"` 直接指向本地源码目录,**改了立刻生效**。

Maven 的做法是 `mvn install` 把 jar 装进 `~/.m2`,再从那儿解析。**这是个关键差异**：Maven 多模块必须先 install,npm workspaces 不用。代价是 npm 的依赖解析结果更难预测（提升、去重、幽灵依赖）。

### 5.3 `paths` 指向 `src` 而不是 `dist`

根 [tsconfig.json](../../tsconfig.json)：

```json
"paths": {
  "@earendil-works/pi-ai":        ["./packages/ai/src/index.ts"],
  "@earendil-works/pi-ai/oauth":  ["./packages/ai/src/oauth.ts"],
  "@earendil-works/pi-ai/*":      ["./packages/ai/src/*.ts", "./packages/ai/src/providers/*.ts"],
  "@earendil-works/pi-agent-core":["./packages/agent/src/index.ts"],
  ...
}
```

注意映射目标是 **`src/*.ts`**,不是 `dist/*.js`。

**收益**：在 `coding-agent` 里改一行代码,`agent` 包的类型变化立刻在 IDE 里可见,不用先 `npm run build`。整个仓库的类型检查（`tsgo --noEmit`）是一次性对**全部源码**做的。

Maven 里没有等价物 —— 你改了 `order-core`,必须 `mvn install` 之后 `order-service` 才看得到。

**代价（重要）**：`paths` 是**开发期视角**,它绕过了 `exports` 白名单。所以：

```ts
// 在 monorepo 内部：能过 ✅（paths 里有 "@earendil-works/pi-ai/*" 通配）
import { something } from "@earendil-works/pi-ai/utils/retry";

// 发布之后，外部用户写同一行：运行时报错 ❌（exports 里没开 ./utils/*）
```

**这是 JS monorepo 的头号经典坑**：本地一切正常,发布后用户报 `ERR_PACKAGE_PATH_NOT_EXPORTED`。

Pi 怎么防的?看 5.4。

### 5.4 边界纪律：用数据说话

我统计了 Pi 里跨包导入的实际情况：

**`agent` 包（12,635 行源码）的全部跨包导入：**

```
17 处  "@earendil-works/pi-ai"           ← 全部走主入口
 4 处  "@earendil-works/pi-telemetry"    ← 全部走主入口
─────
21 处，零深层路径
```

一万两千行代码,跨包引用只有 **21 处**,而且**一次都没有绕过正门**。

**`coding-agent` 包（59,014 行）：**

```
71 处  "@earendil-works/pi-tui"
49 处  "@earendil-works/pi-ai"
37 处  "@earendil-works/pi-agent-core"
15 处  "@earendil-works/pi-ai/compat"          ← 深层路径
 5 处  "@earendil-works/pi-ai/providers/all"   ← 深层路径
 4 处  "@earendil-works/pi-ai/oauth"           ← 深层路径
 ...
```

产品层用了深层路径 —— 但用的全是 `exports` 里**明确开放**的 subpath（`./compat`、`./providers/*`、`./oauth`）,一处越界都没有。

**结论**：`paths` 给了你越界的能力,但这个项目靠纪律不越界。**这就是 A0 那句话的具体样子 —— TS 的架构约束不在编译器里,在人和脚本里。**

那"人"靠不住的时候呢?下一节。

## 第 6 节 · 边界怎么被强制执行

Pi 把边界约束焊进了 `npm run check`。这里讲和 A1 相关的两条。

### 6.1 `check:ts-imports` —— 禁止 `.js` 后缀

[scripts/check-ts-relative-imports.mjs](../../scripts/check-ts-relative-imports.mjs) 用 TypeScript 编译器 API 遍历所有 `.ts` 文件的 AST,找出所有相对导入,**只要后缀是 `.js` 就报错**。

它检查四种位置（说明作者考虑得很全）：

```ts
import { x } from "./a.js";           // ① import 声明
export { x } from "./a.js";           // ② export 声明
const m = await import("./a.js");     // ③ 动态 import
type T = import("./a.js").Foo;        // ④ 类型位置的 import
```

**为什么要有这条规矩**：历史上 TS 项目写 `.js`（因为编译产物是 `.js`）。但 Pi 要让 Node **直接跑 `.ts` 源码**（`tsx` / 原生类型剥离）,那时候路径必须指向真实存在的 `.ts` 文件。**一条规矩,保证了"源码可直接执行"这个能力不被破坏。**

对照 Java：这相当于一条 Checkstyle 规则,但它守护的是一个**架构能力**（免编译运行）,不是代码风格。

### 6.2 `check:browser-smoke` —— 用打包结果断言边界

这条最精彩,值得细看 [scripts/check-browser-smoke.mjs](../../scripts/check-browser-smoke.mjs)。

它做两件事：

**① 浏览器可用性冒烟。** 拿一个入口文件 [scripts/browser-smoke-entry.ts](../../scripts/browser-smoke-entry.ts),里面 import 了所有"应该浏览器安全"的 API：

```ts
import { PiClient } from "@earendil-works/pi-client";
import { createAssistantMessageEventStream, Type } from "@earendil-works/pi-ai";
import { Agent, InMemorySessionRepo, ... } from "@earendil-works/pi-agent-core";
import { decodeCbor, encodeCbor, PROTOCOL_VERSION } from "@earendil-works/pi-protocol";
```

然后用 esbuild 以 `platform: "browser"` 打包。**只要有人不小心在主入口的依赖链里引入了 `node:fs`,打包立刻失败。**

这就是 3.2 里那个"主入口绝不能出现 `node:` import"约束的强制手段。

**② tree-shaking 断言。** 更狠。它打包一个"只用 anthropic 一个 provider"的入口,然后断言产物里：

```js
// 这三个文件绝不能出现在产物里
"packages/ai/src/compat.ts"
"packages/ai/src/models.generated.ts"
"packages/ai/src/providers/all.ts"

// 模型目录 JSON 只能有 anthropic.json 一个
// 厂商 SDK 只能有 @anthropic-ai/sdk 一个
// （openai / @google/genai / @aws-sdk/client-bedrock-runtime 都不许进）
```

**翻译成人话**：「用户只用 Anthropic 时,打出来的包里不许有 OpenAI 和 Google 的 SDK。」

这是一条**架构约束**（按需加载必须真的生效）,被写成了一个**可执行断言**。任何人在 `index.ts` 里手滑加一行 `export * from "./providers/all.ts"`,CI 立刻红。

**Java 对应物**：ArchUnit 的 `noClasses().that().resideInAPackage("..core..").should().dependOnClassesThat().resideInAPackage("..impl..")`。思路完全一样,只是 Pi 用打包产物做断言,粒度更粗但更贴近真实交付物。

> **这一节是本章最重要的认知**：在 TS 里,**架构约束的最终形态是一个能在 CI 里跑的脚本**。你读一个陌生 TS 项目想知道它的架构纪律,`scripts/` 目录和 CI 配置比任何文档都可靠。

## 第 7 节 · 实战：设计一个电商 monorepo

### 7.1 目录结构

```
shop-monorepo/
├── package.json              workspaces: ["packages/*"]
├── tsconfig.base.json        共享编译选项
├── tsconfig.json             paths 映射 + include
├── biome.json                lint + 格式化
├── scripts/
│   └── check-layering.mjs    ← 你自己写的架构守卫
└── packages/
    ├── order-core/           领域模型，零依赖
    │   ├── package.json
    │   └── src/
    │       ├── index.ts      barrel
    │       ├── money.ts
    │       ├── order.ts
```

依赖方向严格单向：`order-core ← order-pricing ← order-service`,`order-core ← order-sdk`。

### 7.2 `order-core`：纯契约包（对标 Pi 的 `telemetry`）

```json
{

  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" }
  },
  "files": ["dist"],
  "dependencies": {}
}
```

```ts
// src/index.ts —— 一个门，零依赖，零副作用
```

```ts
// src/order.ts

   skuId: string;

   unitPrice: Money;

   id: string;
   buyerId: string;
   items: readonly OrderItem[];
```

Spring 对照：一个只有 record / DTO 的 `order-core` 模块,`<dependencies>` 为空。**唯一区别是 TS 版本里这些接口编译后完全消失,运行时不存在 `Order` 这个东西。** 所以如果要从 HTTP 反序列化出 `Order`,必须额外写运行时校验（A2 会讲）。

```ts
// 注意：策略实现不在这里，走 ./strategies/* subpath 按需引

```

```
├── index.ts
├── types.ts               PricingStrategy 接口
├── calculator.ts          编排：依次应用策略
├── strategies/
│   ├── coupon.ts          优惠券（可能依赖优惠券服务 SDK，很重）
│   ├── full-reduction.ts  满减
│   └── member.ts          会员折扣（依赖会员系统 SDK，很重）
```

### 7.6 自己写架构守卫

因为 `paths` 允许越界,得自己拦。最小可用版本（抄 Pi 的 `check-ts-relative-imports.mjs` 思路）：

```js
// scripts/check-layering.mjs
import { readFileSync, readdirSync } from "node:fs";
import { join } from "node:path";

// 允许的依赖方向：谁能 import 谁
const ALLOWED = {
   "order-core":    new Set([]),
   "order-pricing": new Set(["@shop/order-core"]),
   "order-service": new Set(["@shop/order-core", "@shop/order-pricing"]),
   "order-sdk":     new Set(["@shop/order-core"]),
};

const failures = [];

function walk(dir, fn) {
   for (const e of readdirSync(dir, { withFileTypes: true })) {
      const p = join(dir, e.name);
      if (e.isDirectory()) { if (e.name !== "node_modules" && e.name !== "dist") walk(p, fn); }
      else if (e.name.endsWith(".ts")) fn(p);
   }
}

for (const pkg of Object.keys(ALLOWED)) {
   walk(`packages/${pkg}/src`, (file) => {
      const src = readFileSync(file, "utf8");
      for (const m of src.matchAll(/from\s+"(@shop\/[^"]+)"/g)) {
         const spec = m[1];
         const target = spec.split("/").slice(0, 2).join("/");   // @shop/order-core
         if (!ALLOWED[pkg].has(target)) {
            failures.push(`${file}: ${pkg} 不允许依赖 ${target}`);
         }
      }
   });
}

if (failures.length) { console.error(failures.join("\n")); process.exit(1); }
```

挂到 `npm run check` 里,这就是你的 ArchUnit。

**三十行代码,换来编译器不提供的分层强制。** 这就是"手搓"的真实体量 —— 不算大,但确实得自己写,而且每个项目都得写一遍。

```
── 三级边界 ─────────────────────────────────────────
文件级   export / 不 export        ≈ public / private（没有中间档）
包级     package.json exports      ≈ module-info.java exports
         src/index.ts              ≈ Facade 类（决定主入口有哪些符号）
仓库级   workspaces + tsconfig paths ≈ Maven modules（但指向 src 不是 dist）

── 读一个陌生 TS 包，先看这四处 ──────────────────────
1. package.json exports      入口数量和形状 → 想被怎么用
2. package.json dependencies 数量和内容     → 库还是框架
3. src/index.ts 行数         暴露面宽窄     → 库还是产品层
4. scripts/ + CI             架构纪律的真身  → 边界靠什么强制

── 五条可以直接照抄的规矩 ────────────────────────────
1. 只用命名导出，不用 default export
2. 包内文件走相对路径引具体文件；只有包外才走 barrel
3. 主入口保持 side-effect free；重的实现放 subpath
4. 纯类型引用一律 import type
5. 分层约束写成 CI 脚本，别指望 review 兜住

── 本章 Pi 源码锚点 ─────────────────────────────────
packages/ai/src/index.ts              47 行   刻意做窄的门 + 顶部那段注释

packages/agent/package.json            —      四入口 exports
packages/ai/package.json               —      通配 subpath exports
tsconfig.json                          —      paths 指向 src
scripts/check-ts-relative-imports.mjs  —      AST 级导入规则
scripts/check-browser-smoke.mjs        —      ★ 用打包产物断言架构约束

── 关键数据 ─────────────────────────────────────────
```
